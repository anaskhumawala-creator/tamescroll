## B1 — EXPOSURE. The corpus arm models a WIPE; the app DEMOTES, and the exposure column is 95% artefact

keeping the OTA ceiling at 75.

**WHAT THE ARM DOES.** `app/gaze/bench/arch-arms.mjs:280`


**WHAT THE APP DOES.** `app/gaze/src/init-entry.js:2115`

persist so coverage holds through the pass gap, but every verdict state resets to
blurred"*. The two source files directly contradict each other, and the arm has

## B3 — DEAD-CHECK. `faceNoShape 48 → 0` is not explained by the mechanism given, and no counter can tell

`faceNoShape` 48 -> 0. The ghost gate cannot fire on a pass that ran no model, by

```
  if (emptyRun < PERSON_EMPTY_STREAK) return true;
```

and the repo's own test asserts it: *"backed off, it still runs one pass in three

`app/gaze/src/worker-entry.js:286` sets
`noHumanShape: person ? !!persons.noHumanShape : false`, so the gate is disarmed

So the stated mechanism predicts **~48/3 ~= 16**, not 0. The doc reports 0 and
attributes it to a mechanism that cannot produce it. Its derived phantom figure

## B6 — NIT. "92.8-95.9% of hard cuts" is recall on a population selected by a correlate of the gate's own input

`node cut-truth.mjs` reproduces §10j's table **exactly**, including the pairing
sweep (offset 0: p05 46.6 / p50 59.8 / p75 68.1 against 1.7 and 2.4 either side)
and every recall row. The numbers are not in dispute.

What is, is what they are recall *on*. The tool's own output prints the at-a-cut
median of **our** delta per scdet row:

```
scdet >= 8   (at a cut: p05 25.9  p50 48.7  p95 77.5)   @60 = 20.9%
scdet >= 15  (at a cut: p05 38.3  p50 52.0  p95 80.8)   @60 = 26.3%
scdet >= 20  (at a cut: p05 46.6  p50 59.8  p95 92.8)   @60 = 49.3%
scdet >= 25  (at a cut: p05 58.5  p50 75.0  p95 125.2)  @60 = 92.8%
scdet >= 30  (at a cut: p05 73.7  p50 93.5  p95 153.2)  @60 = 95.9%
```

Raising the scdet threshold raises the selected population's **own delta**
monotonically, 48.7 → 93.5. A6 measured `pearson(our delta, scdet) = 0.498`, so
"hard cut" as operationalised here partly means "a cut our own statistic already
scores high" — and at scdet >= 30 the population median (93.5) sits well above the
gate (60), which is why recall there is near-total.

§10j does disclose the row-selection sensitivity (*"the row you pick IS the answer
you get"*) and does disclose that scdet is a luma measurement. It does not
disclose that the selection and the gate share the statistic, which is what makes
the top rows flattering. The headline comparison in the commit ("92.8-95.9%, not
45.5%") remains fair for the scdet >= 30 row, which is where the old 45.5% came
from — but that population is **121 cuts over 4.2h**, the sample-size point A2
already made.

**FALSIFIER.** Quote the recall figure with its scdet row attached everywhere it
appears, and put the unfiltered row (20.9% @60, scdet >= 8) beside it.

## B7 — NIT. §10i has no artifact at all, n=1 per arm, and a fixed arm order

**CLAIM AUDITED.** The whole §10i table: reads 63/63, reads/s 0.627 vs 0.629
(1.00x), rAF 2424 (24.1 Hz) vs 3368 (33.6 Hz), covered 61.6% vs 62.0%,
passDropped 20 vs 11, faceNoShape 48 vs 0.

**NO ARTIFACT EXISTS.** `spikes/gauntlet/probe_skip_ab.py` never writes to disk
(`grep -n "open(\|json.dump\|write"` matches only a `json.dumps` inside a
JavaScript string literal); commits `8a9ed82` and `712cec0` touch no file under
`spikes/`; and

```
$ grep -rl "3368\|33\.6" docs/ spikes/gauntlet/*.py spikes/gauntlet/*.txt
docs/engine-findings.md
```

Every number in §10i exists **only in my prose** — which is the one input
`docs/critic-loop.md` §5.1 excludes from the packet, and §5.2 names this as
exactly the case Phase B exists to catch.

**THE INSTRUMENT SURVIVES ITS OBVIOUS ATTACK — recorded because a clean bill
should list what was checked.** The probe does prove the dial took effect in both
arms rather than assuming it: it composes an accessor over the app's own
`__TS_GAZE_TUNING__` write and then

```
if not tuned or '"PERSON_SKIP_EVERY":%d' % skip_every not in str(tuned):
    raise SystemExit("ARM DID NOT TAKE THE DIAL: ...")
```

So "both arms silently ran the shipped value" is guarded.

**WHAT IS NOT GUARDED.** The arms run `for n in (1, 3)` in a fixed order in one
process, arm 1 always first. HTTP cache, model files and compiled shaders are warm
for arm 3 and cold for arm 1. rAF rising 24.1 → 33.6 Hz on the second arm is
consistent with the skip **and** with a warm second navigation, and nothing in the
repo separates them: there is no reversed-order run and no repeat. The header
argues correctly for pairing within a session (*"pass cost varies by more between
sessions than the effect"*) and does not address within-session order.

**AND THE EQUIVALENCE CLAIMS ARE NOT SUPPORTED AT THAT n.** "reads/s flat at
1.00x" rests on 63 events per arm; the Poisson band on 63 counts is +/-sqrt(63) ~= 8,
so the ratio carries roughly a +/-25% 95% interval and cannot exclude a real cadence
gain of a fifth. **IT DOES NOT BUY VERDICTS** is set in bold on that. "covered
61.6% vs 62.0%" is the same shape. §10i does hedge the *mechanism* (*"WHY THE
CADENCE DID NOT MOVE IS UNMEASURED"*) but not the *power*.

**FALSIFIER.** Have `probe_skip_ab.py` write its result dict to
`spikes/gauntlet/skip-ab-<label>.json`, and run it at least twice with the arm
order reversed on the second run. If rAF still rises with the skip when the skip
arm goes first, the frame-rate win is real; if it tracks arm order instead, it is
the warm cache.
