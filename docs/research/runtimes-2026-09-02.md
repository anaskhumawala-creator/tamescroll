# Browser inference runtimes for tamescroll — survey (2026-09-02)

Question asked: *what is the fastest CORRECT runtime for real-time video-frame
inference in 2026*, given this app's exact situation — a Web Worker inside
**Android System WebView** and **Windows WebView2**, running on a **third-party
page whose CSP and response headers we do not control** (youtube.com,
reddit.com, x.com, instagram.com), inside a Tauri v2 shell. Today: TensorFlow.js
on the WebGL backend, one MoveNet MultiPose pass ~**500 ms** on an Adreno 610
and ~**3000 ms** on a lower-end device.

Every factual claim carries a source URL. Where a number comes from a vendor
blog with no primary equivalent it is **flagged as such**. Where the evidence
does not exist, this document says so instead of guessing.

> **Provenance.** This file replaces an earlier 406-line survey of the same
> question committed at `df4755a`; that version is recoverable with
> `git show df4755a:docs/research/runtimes-2026-09-02.md`. Everything it found
> that this one did not — the MobileNetV2 WebGPU microbenchmark (§1d), the
> Qualcomm QNN/NPU reality for an Adreno 610 (§6c, §8), the ORT Mobile
> binary-size figure, the iOS bridge pattern — has been merged in here. The
> substantive corrections this version makes to it are: TF.js is frozen (§2a),
> Chromium's Android WebGPU gate read from source rather than from blogs (§1a),
> `android_webview/` does **not** disable WebGPU (§1b), Android WebView **does**
> have a binary JS↔native channel (`WebMessageCompat` ArrayBuffer) and Tauri's
> own IPC is JSON-only on Android (§6a), and tfjs quantization is proven
> dequantize-at-load from source rather than inferred from doc phrasing (§8).

**Status vocabulary, used strictly throughout.** These are not interchangeable
and the difference between them is most of the report:

| Category | Meaning here |
|---|---|
| **SHIPPING** | On by default, no flag, on the hardware class this app actually runs on (mid-range Android, Android 12+, Adreno/Mali) |
| **SHIPPING-DESKTOP** | On by default on Windows / macOS / ChromeOS only |
| **FLAG** | Present but needs a `chrome://flags` toggle or a command-line switch — not shippable to a user |
| **ORIGIN TRIAL** | Needs a per-origin, expiring token — structurally impossible for us, because the origins are YouTube's, not ours |
| **UNVERIFIED** | Code paths exist, no primary source confirms behaviour on our target; must be probed on the device |
| **PROPOSAL** | Spec/repo only |

## 0. The short version

1. **The most consequential fact in this survey: TensorFlow.js is frozen.**
   Last stable release `tfjs-v4.22.0`, **2024-10-21**; the npm entry for
   `@tensorflow/tfjs` has not been modified since **2025-01-08** (a
   `4.23.0-rc.0` that never shipped); last commit on master **2026-04-06**.
   That is **22 months with no release**.
   ([GitHub releases API](https://api.github.com/repos/tensorflow/tfjs/releases/latest),
   [npm registry](https://registry.npmjs.org/@tensorflow/tfjs))
   Google's own successor messaging is explicit: LiteRT.js is "a powerful
   evolution from TensorFlow.js for executing .tflite models", and prior web AI
   solutions "like TensorFlow.js relied on less performant JavaScript-based
   kernels"
   ([Google Developers Blog, 2026-07-09](https://developers.googleblog.com/litertjs-googles-high-performance-web-ai-inference/)).
   Whatever else is decided, the current runtime is a **decaying asset** and no
   upstream fix is coming for anything found in it.

2. **Before changing runtime, question the number itself.** tfjs on the
   **WebGL** backend ran MoveNet SinglePose Lightning at **34 FPS (~29 ms) on a
   Pixel 5** — Adreno 620, one class above an Adreno 610
   ([TF blog, 2021-05](https://blog.tensorflow.org/2021/05/next-generation-pose-detection-with-movenet-and-tensorflowjs.html)).
   MultiPose is heavier than SinglePose, but it is not 17x heavier. A 500 ms
   MultiPose pass on an Adreno 610 sits **far outside** what this runtime is
   known to do on that hardware class, which means the dominant cost may not be
   the runtime at all. Candidates, all priced in §7: shader recompiles from
   varying input shapes, GPU→CPU readbacks, and GPU contention with YouTube's
   own compositing. **Do not port a pipeline to a new runtime to fix a defect
   that lives in the old one's configuration.**

3. **The cheapest real lever available today is `tf.setBackend('webgpu')`
   behind a feature detect** — same models, same tfjs API, no conversion, no
   re-validation of verdicts. Kernel coverage is not the blocker (§2b). The
   blocker is one unknown: *does `navigator.gpu` exist in Android System
   WebView on his phone?* Nothing in Chromium's `android_webview/` disables it,
   and the Android blocklist admits Qualcomm on Android 12+, but no primary
   source confirms WebView exposure (§1b). **That is a five-line probe and it
   gates everything below it.**

4. **The durable answer, if a port is on the table, is ONNX Runtime Web**
   (WebGPU EP, single-threaded WASM+SIMD fallback): released **1.29.0 on
   2026-08-24** with dev builds published daily
   ([npm](https://registry.npmjs.org/onnxruntime-web)), **full `ai.onnx`
   operator coverage on the WASM EP**, and its own compatibility table claiming
   WebGPU works on **Chrome/Edge Android**
   ([js/web/README.md](https://github.com/microsoft/onnxruntime/blob/main/js/web/README.md)).
   The cost is not engineering hours, it is **re-validating every verdict** —
   this repo has already measured that a numerics change flips 8 of 100 gender
   verdicts.

5. **Nothing in the "hardware NPU" direction is reachable from a WebView.**
   WebNN is ORIGIN TRIAL, desktop-only, and Android + Android WebView were
   *explicitly removed* from the trial. NNAPI is deprecated as of Android 15.
   In 2026 an NPU is reachable from Kotlin and from nowhere else (§4).

## 1. WebGPU

### 1a. Chrome for Android — SHIPPING, and an Adreno 610 qualifies

Enabled by default since **Chrome 121**: *"WebGPU is now enabled by default in
Chrome 121 on devices running Android 12 and greater powered by Qualcomm and
ARM GPUs"*
([Chrome for Developers — What's New in WebGPU 121](https://developer.chrome.com/blog/new-in-webgpu-121)).
The Intent to Ship (2023-10-28, targeting M121) covers "Adreno and Mali GPUs
(majority of mobile market)" on Android 12+
([blink-dev: Intent to Ship: WebGPU on Android](https://groups.google.com/a/chromium.org/g/blink-dev/c/YFWuDlCKTP4)).

The authoritative gate is in Chromium HEAD, not in a blog. From
[`gpu/config/webgpu_blocklist_impl.cc`](https://chromium.googlesource.com/chromium/src/+/HEAD/gpu/config/webgpu_blocklist_impl.cc):

```c++
#if BUILDFLAG(IS_ANDROID)
  constexpr uint32_t kARMVendorID = 0x13B5;
  constexpr uint32_t kQualcommVendorID = 0x5143;
  constexpr uint32_t kIntelVendorID = 0x8086;
  constexpr uint32_t kImgTecVendorID = 0x1010;

  switch (info.vendorID) {
    case kARMVendorID:
    case kQualcommVendorID:
    case kIntelVendorID:
      // ARM, Qualcomm, and Intel GPUs are supported on Android 12+ on Vulkan
      if (info.backendType == wgpu::BackendType::Vulkan &&
          (base::android::android_info::sdk_int() <
           base::android::android_info::SDK_VERSION_S)) {
        reason = reason | WebGPUBlocklistReason::AndroidLimitedSupport;
      }
      // and Android 10+ on OpenGLES (currently Chrome's minimum, so no version
      // check here)
      break;

    case kImgTecVendorID:
      // Imagination GPUs are supported on Android 16+ on Vulkan
      ...
    default:
      // Other OS versions/GPU vendor combinations may be fine, but have not had
      // sufficient testing yet.
      reason = reason | WebGPUBlocklistReason::AndroidLimitedSupport;
```

Read straight off that source:

| Vendor | Vulkan backend | OpenGLES backend |
|---|---|---|
| **Qualcomm / Adreno (`0x5143`)** | Android **12+** | Android **10+** (no version check) |
| ARM / Mali (`0x13B5`) | Android 12+ | Android 10+ |
| Intel (`0x8086`) | Android 12+ | Android 10+ |
| Imagination / PowerVR (`0x1010`) | Android **16+** | Android 13+ |
| **everything else, incl. Samsung Xclipse** | **blocked** | **blocked** |

The gpuweb wiki's per-vendor table agrees and adds the Xclipse target:
ARM/Qualcomm/Intel since Chrome 121 on Android 12+, Imagination since Chrome
139 on Android 16+, Samsung Xclipse "probably 154" on Android 12+
([gpuweb Implementation Status](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)).

Two further kills in the same file worth knowing:

- An adapter reporting `AdapterType::CPU` is blocklisted
  (`WebGPUBlocklistReason::CPUAdapter`). **This is why the emulator cannot
  answer this question** — under swiftshader there is no hardware adapter to
  hand out. That is the same emulator-can't-answer wall this repo has hit
  repeatedly; do not spend a night on it.
- `kAAPMBlocksWebGPU`, `FEATURE_ENABLED_BY_DEFAULT` — *"Feature enforces WebGPU
  security in Android Advanced Protection Mode"*
  ([`gpu/config/gpu_finch_features.cc`](https://chromium.googlesource.com/chromium/src/+/HEAD/gpu/config/gpu_finch_features.cc)).
  A user with Advanced Protection Mode enabled has no WebGPU at all. Feature
  detection is not optional, it is the design.

**For his phone (Adreno 610, Android 16):** vendor `0x5143`, SDK 36 >= S. Not
blocklisted. In *Chrome*, WebGPU would be available.

### 1b. Android System WebView — UNVERIFIED, and this is the load-bearing unknown

No primary source states it either way. What the evidence does say:

- `kWebGPUService` is **`FEATURE_ENABLED_BY_DEFAULT` when
  `BUILDFLAG(IS_ANDROID)`**, and Android WebView is an `IS_ANDROID` build
  ([`gpu_finch_features.cc`](https://chromium.googlesource.com/chromium/src/+/HEAD/gpu/config/gpu_finch_features.cc)):

  ```c++
  // Enable WebGPU on gpu service side only. This is used with origin trial and
  // enabled by default on supported platforms.
  #if BUILDFLAG(IS_APPLE) || BUILDFLAG(IS_WIN) || BUILDFLAG(IS_CHROMEOS) || \
      BUILDFLAG(IS_ANDROID) || BUILDFLAG(USE_WEBGPU_ON_VULKAN_VIA_GL_INTEROP)
  #define WEBGPU_ENABLED base::FEATURE_ENABLED_BY_DEFAULT
  ```

- **Nothing in `android_webview/` disables it.** WebView's feature-disable list
  in
  [`android_webview/lib/aw_main_delegate.cc`](https://chromium.googlesource.com/chromium/src/+/HEAD/android_webview/lib/aw_main_delegate.cc)
  turns off shared workers, the File System API, Notifications, Push,
  Presentation, Remote Playback, Media Session and others — **WebGPU is not
  among them**. `android_webview/common/aw_features.cc` and
  `android_webview/browser/aw_content_browser_client.cc` contain no WebGPU
  reference at all.
- **WebView's own production flag list carries WebGPU toggles** —
  `GpuFeatures.WEB_GPU_USE_SPIRV14` ("Use WebGPU's SPIR-V 1.4") and
  `GpuFeatures.AAPM_BLOCKS_WEB_GPU` ("Android Advanced Protection Mode (AAPM)
  blocks WebGPU for At-Risk Users") — in
  [`ProductionSupportedFlagList.java`](https://chromium.googlesource.com/chromium/src/+/HEAD/android_webview/java/src/org/chromium/android_webview/common/ProductionSupportedFlagList.java).
  Exposing those in WebView's dev UI only makes sense if WebGPU code paths can
  run in WebView.
- Chromium also carries `kWebGPUAndroidOpenGLES` (enabled by default) and a
  `USE_WEBGPU_ON_VULKAN_VIA_GL_INTEROP` build path — a GLES-backed WebGPU
  exists precisely for cases where Vulkan is not the compositing backend, which
  is WebView's situation (WebView composites through a draw functor and
  *disables* `kVulkan`, using `kWebViewDrawFunctorUsesVulkan` instead — see the
  comment at `gpu_finch_features.cc`: *"Note Android WebView uses
  kWebViewDrawFunctorUsesVulkan instead of this."*).
- **Against all that:** [caniwebview.com's WebGPU
  page](https://caniwebview.com/features/web-feature-webgpu/) (last updated
  **2026-08-29**) still lists support as **unknown (`*`) for both Android
  WebView and WebView2**.

**A trap to avoid:** the official-looking
[developer.android.com/develop/ui/views/graphics/webgpu](https://developer.android.com/develop/ui/views/graphics/webgpu)
page is about the **Jetpack `androidx.webgpu` Kotlin bindings** (1.0.0-alpha05,
2026-04-22 — [release
notes](https://developer.android.com/jetpack/androidx/releases/webgpu)), a
native-code library **unrelated to WebView**. It is not WebView evidence and
must not be cited as such.

**So: probable, unproven, and cheap to settle.** In a Worker on the real phone,
read-only, no page mutation:

```js
const a = navigator.gpu && await navigator.gpu.requestAdapter();
report({ hasGpu: !!navigator.gpu, adapter: !!a, info: a && {
  vendor: a.info.vendor, architecture: a.info.architecture,
  device: a.info.device, description: a.info.description,
  isFallbackAdapter: a.info.isFallbackAdapter } });
```

`GPUAdapterInfo` exposes exactly `vendor`, `architecture`, `device`,
`description`, `subgroupMinSize`, `subgroupMaxSize`, `isFallbackAdapter`
([WebGPU spec, GPUAdapterInfo](https://www.w3.org/TR/webgpu/)). Note the API
shape: it is the **`adapter.info` attribute**;
`GPUAdapter.requestAdapterInfo()` is gone from the spec — see §2a for why that
matters to tfjs specifically.

**WebGPU in a Worker is spec-guaranteed, so it is not a separate question.**
Every WebGPU interface is declared `[Exposed=(Window, Worker), SecureContext]`
and the spec states `WorkerNavigator includes NavigatorGPU`
([spec source `index.bs`](https://github.com/gpuweb/gpuweb/blob/main/spec/index.bs)).
Chrome added service-worker and shared-worker support by 124
([What's New in WebGPU](https://developer.chrome.com/blog/new-in-webgpu-121)).

**And WebGPU is CSP-clean, which is not a small thing here.** WGSL shader
source is not script: it is passed to `createShaderModule()` as a string and is
governed by no CSP directive. Unlike a blob Worker (dead on YouTube under
`require-trusted-types-for 'script'`, established in this repo) or ORT's proxy
worker, nothing about WebGPU needs a CSP allowance, an eval, or a header we
cannot set.

### 1c. WebView2 on Windows — SHIPPING (inherited), D3D12 backend

WebGPU shipped in Chrome/Edge **113** on Windows (Direct3D 12), macOS and
ChromeOS
([gpuweb Implementation Status](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)).
WebView2 is the same Chromium engine on the Edge release train: Edge 152
(2026-08-27) ships "WebGPU: Subgroup Size Control" among its web-platform
features, and its release notes point at WebView2 Runtime 152.0.4191.53
([Edge 152 web platform release notes](https://learn.microsoft.com/en-us/microsoft-edge/web-platform/release-notes/152)).

Microsoft has never documented WebGPU-in-WebView2 specifically. The closest
first-party-adjacent statement is on the WebView2Feedback Xbox discussion,
where a tester reports *"It works in WebView2 on Windows"* and the maintainer
routes the Xbox case to a separate feature request
([WebView2Feedback discussion #4138](https://github.com/MicrosoftEdge/WebView2Feedback/discussions/4138)).
ONNX Runtime's own compatibility matrix marks WebGPU ✔ for Chrome/Edge on
Windows, requiring Chromium >= 113
([js/web/README.md](https://github.com/microsoft/onnxruntime/blob/main/js/web/README.md)).

**Treat as available; still feature-detect.** The same blocklist machinery
applies — a blocklisted driver yields no adapter
([Chrome WebGPU troubleshooting](https://developer.chrome.com/docs/web-platform/webgpu/troubleshooting-tips)),
and `webgpu_blocklist_impl.cc` additionally refuses any adapter whose
`backendType` is `D3D11`, so a machine that falls back off D3D12 gets nothing.

### 1d. Measured WebGPU-vs-WebGL speedup for our model class — **no such number exists**

Stated plainly because it decides how much to bet: there is **no published
benchmark of WebGPU vs WebGL for a pose- or face-detection-class CNN on
mid-range Android**. What does exist:

- Chrome's I/O 2023 post: *"an initial port of an image diffusion model in
  TensorFlow.js shows a 3x performance gain on a variety of hardware when moved
  from WebGL to WebGPU"* — a diffusion model, unnamed hardware, described by
  its own authors as "an early port"
  ([developer.chrome.com/blog/webgpu-io2023](https://developer.chrome.com/blog/webgpu-io2023)).
  **Vendor blog, no primary equivalent, and the wrong model class.**
- Chrome's WebGPU release announcement claims *"more than three times
  improvement in machine learning model inferences"* versus WebGL, with no
  published methodology
  ([developer.chrome.com/blog/webgpu-release](https://developer.chrome.com/blog/webgpu-release)).
  **Vendor blog, unmethodised. Treat as an upper bound, not a forecast.**
- LiteRT.js claims "up to 3x across both CPU and GPU inference" versus other
  web runtimes, and "5-60x speedup compared to standard CPU execution" for
  GPU/NPU — measured on a **2024 MacBook Pro (M4)**
  ([Google Developers Blog, 2026-07-09](https://developers.googleblog.com/litertjs-googles-high-performance-web-ai-inference/)).
  **Vendor blog; desktop Apple silicon; says nothing about Adreno.**
- The one number of the right *shape* — a small CNN, warm and cold separated —
  is a third-party MobileNetV2 microbenchmark: **~30% faster steady state
  (9.5 ms WebGPU vs 13.6 ms WebGL per inference after warm-up)** but a much
  **cheaper cold start (483 ms WebGPU vs 1421 ms WebGL first inference)**
  ([Joan León, "ML in the browser with WebGPU"](https://joanleon.dev/en/webgpu-ml-browser/)).
  **Independent blog, no primary equivalent, desktop, and MobileNetV2 is not
  MoveNet MultiPose — flagged accordingly.**

The mechanism to expect for a small CNN is compute shaders replacing
fragment-shader-with-texture-packing, fewer driver round trips, and no
float-texture emulation. Real, but the 3x figure describes a workload nothing
like MoveNet. **Plan around "~30% warm, materially better cold", treat 3x as a
ceiling, and measure the arm on the device before believing either.**

The cold-start half is worth noticing separately: this app already spends
**1163 ms on pure shader compile** in warm-up on his phone, and pays it again
whenever input shapes churn. If the MobileNetV2 cold-start ratio holds at all,
WebGPU's pipeline-creation model may be worth more to this pipeline than its
steady-state throughput is.

### 2a. Project health — the framing fact

| Package | Latest stable | Published | npm entry last modified |
|---|---|---|---|
| `@tensorflow/tfjs` | 4.22.0 | 2024-10-21 | 2025-01-08 |
| `@tensorflow/tfjs-backend-webgpu` | 4.22.0 | 2024-10-21 | 2025-01-08 |
| `@tensorflow/tfjs-backend-wasm` | 4.22.0 | 2024-10-21 | 2025-01-13 |

([npm registry](https://registry.npmjs.org/@tensorflow/tfjs);
[GitHub releases API](https://api.github.com/repos/tensorflow/tfjs/releases/latest))
Last commit on `master`: **2026-04-06**. There is no deprecation notice on the
repo — but there is also no release, and a `4.23.0-rc.0` has sat unreleased
since January 2025.

**This has a concrete failure mode for the WebGPU option.** tfjs 4.22.0's
changelog contains *"fix: conditionally call deprecated
`GPUAdapter.requestAdapterInfo`"* — the last release was already patching
around WebGPU API churn, and `requestAdapterInfo()` has since been replaced by
the `adapter.info` attribute in the spec
([WebGPU spec](https://www.w3.org/TR/webgpu/)). Adopting
`tfjs-backend-webgpu` means adopting a **frozen consumer of a spec that is
still moving**, with nobody upstream to fix the next break. Pin the version,
and own that risk explicitly rather than discovering it in a release.

### 2b. `webgpu` vs `webgl` kernel coverage — **not a blocker for our models**

Counted directly from `register_all_kernels.ts` on master:

| Backend | registered kernels |
|---|---|
| `tfjs-backend-cpu` | 172 |
| `tfjs-backend-webgl` | 170 |
| `tfjs-backend-webgpu` | **162** |

The exact 12-kernel gap (present in webgl, missing from webgpu):
`BatchNorm`, `BitwiseAnd`, `NonMaxSuppressionV4`, `RaggedGather`,
`RaggedRange`, `RaggedTensorToTensor`, `SparseFillEmptyRows`, `SparseReshape`,
`StaticRegexReplace`, `StringSplit`, `StringToHashBucketFast`, `Unique`.
(webgpu additionally has `FusedBatchNorm`, `Draw` and two `Dilation2D` grads
that webgl lacks.)

Everything a BlazeFace / MoveNet / faceres pipeline touches **is present** on
webgpu: `Conv2D`, `DepthwiseConv2dNative`, `FusedConv2D`,
`FusedDepthwiseConv2D`, `MaxPool`, `AvgPool`, `MaxPoolWithArgmax`,
`ResizeBilinear`, `ResizeNearestNeighbor`, `CropAndResize`, `ArgMax`,
`GatherNd`, `GatherV2`, `TopK`, `Transpose`, `Cast`, `Einsum`,
`NonMaxSuppressionV3`, `NonMaxSuppressionV5`. Only `NonMaxSuppressionV4` is
absent — and this repo already does NMS in JS (`app/gaze/src/nms.mjs`), so it
would not be reached.
([register_all_kernels.ts — webgpu](https://github.com/tensorflow/tfjs/blob/master/tfjs-backend-webgpu/src/register_all_kernels.ts),
[webgl](https://github.com/tensorflow/tfjs/blob/master/tfjs-backend-webgl/src/register_all_kernels.ts))

The backend's README is candid about maturity: *"The mission of WebGPU backend
is to achieve the best performance among all approaches. However, this target
can not be met overnight"* — and it names BlazeFace, PoseDetection and
MobileNet among supported models
([README](https://github.com/tensorflow/tfjs/blob/master/tfjs-backend-webgpu/README.md)).

**Consequence: switching backend is one line plus a feature detect, with a
small enumerable op risk that is settled by loading the three models once and
watching for a "kernel not registered" throw.**

### 2c. `wasm` backend, and why multithreading is unavailable to us — CONFIRMED DEAD

This is the constraint that has to be exactly right, and it is:

1. `SharedArrayBuffer` requires the page to be **cross-origin isolated**, which
   requires **`Cross-Origin-Opener-Policy: same-origin` and
   `Cross-Origin-Embedder-Policy: require-corp` response headers on the
   top-level document**
   ([web.dev — cross-origin isolation guide](https://web.dev/articles/coop-coep)).
2. Those headers come from **YouTube's server, on YouTube's response, for
   YouTube's document**. An injected script cannot add them; nothing in the
   platform lets injected content retroactively isolate a document it did not
   serve. The service-worker COEP-shim workaround is also closed: a service
   worker can only be registered on an origin you control, and we control none
   of these four.
3. tfjs states the consequence itself: *"Starting Chrome 92, cross-origin
   isolation needs to be set up ... to take advantage of the multi-threading
   support"*, listing those two headers; without them it reverts to SIMD-only
   or vanilla WASM
   ([tfjs-backend-wasm README](https://github.com/tensorflow/tfjs/blob/master/tfjs-backend-wasm/README.md)).
4. ONNX Runtime Web enforces the same, in source —
   [`js/web/lib/wasm/wasm-factory.ts`](https://github.com/microsoft/onnxruntime/blob/main/js/web/lib/wasm/wasm-factory.ts):

   ```ts
   const isMultiThreadSupported = (): boolean => {
     // If 'SharedArrayBuffer' is not available, WebAssembly threads will not work.
     if (typeof SharedArrayBuffer === 'undefined') { return false; }
   ```

   and the docs: *"Only when the browser supports WebAssembly multi-threading
   and `crossOriginIsolated` mode is enabled, multi-threading will be
   enabled"*
   ([ORT env flags and session options](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html)).

**So on every platform page this app touches, any WASM runtime is
single-threaded, permanently.** Both runtimes degrade silently and correctly —
no crash, just one thread. Already recorded as a dead end in
`blur-architectures-2026-08-24.md`; re-confirmed here from source, and it
should never be re-litigated.

**Quantifying the single-thread penalty.** No clean 1-thread-vs-N-thread
ablation is published for our model class. The nearest primary datapoints are
in the MoveNet blog, for WASM **with SIMD + multithread**: Lightning 42 FPS on
a 2019 MacBook Pro 15" against **104 FPS on WebGL** on the same machine;
Thunder 21 vs 77
([TF blog](https://blog.tensorflow.org/2021/05/next-generation-pose-detection-with-movenet-and-tensorflowjs.html)).
On that hardware the *best-case* WASM path — threads available — was already
**2.5–3.7x slower than WebGL**, and we cannot even have the threads. The
tfjs-wasm README's framing matches: for "medium-sized" models (100–500M ops)
WASM is *"several times slower than the WebGL backend"*, and only "comparable"
for lite models of 20–60M ops.

**Conclusion: single-threaded WASM+SIMD is a correctness fallback, not a speed
plan.** It is the right thing to fall back *to* when no GPU adapter exists; it
is never the thing to move *to*.

recommended to use WebGPU for better performance."*; `[5]` WebNN *"Requires to
launch browser with commandline flag
`--enable-features=WebMachineLearningNeuralNetwork`"* (i.e. FLAG, not
shippable). The same README says the WebGPU backend *"is still an
**experimental feature**"* while the WASM backend *"currently support[s] all
operators in `ai.onnx` and `ai.onnx.ml`"*.

That asymmetry is the point. **ORT's CPU fallback is complete**, where tfjs's
WASM backend is a partial reimplementation. If a graph will not run on WebGPU,
the WASM EP still runs it correctly (slowly). For a fail-closed protection
pipeline that is a materially better safety property than what ships today.

Note the Android row's footnote text reads "on Windows" — a copy-paste slip in
ORT's table. The ✔ in the Android column is the claim; the version footnote is
unreliable. The WebGPU EP tutorial states it more cleanly: *"WebGPU is
available out-of-box in latest versions of Chrome and Edge on Windows, macOS,
Android and ChromeOS"*
([Using the WebGPU EP](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html)).
**Neither statement says anything about Android *WebView*** — §1b's unknown is
unchanged by choosing ORT.

### 3c. WebGPU EP operator coverage

109 operator rows in
[`js/web/docs/webgpu-operators.md`](https://github.com/microsoft/onnxruntime/blob/main/js/web/docs/webgpu-operators.md).
Relevant to us: `Conv` (ai.onnx 1-10, 11+, plus an NHWC internal domain,
annotated *"need perf optimization; conv3d is not supported"*),
`ConvTranspose`, `MaxPool`, `AveragePool`, `GlobalAveragePool`, `Resize`,
`Gather`, `Transpose`, `Softmax`, `DepthToSpace`, `DequantizeLinear`,
`MatMulNBits`, `GatherBlockQuantized`, `FusedConv`. **Absent:
`NonMaxSuppression` and `TopK`.**

There is no separate depthwise-convolution operator in ONNX — depthwise is
`Conv` with `group == channels`, covered by the `Conv` row.

The absent ops matter procedurally, not fatally: ORT will silently run an
unsupported node on the CPU EP, which for a node in the middle of a graph means
a **GPU→CPU→GPU round trip per frame**. Any port must dump the partition
(`sessionOptions.logSeverityLevel` / the EP-assignment log) and confirm the
whole conv stack landed on WebGPU, rather than trusting that it did.

### 3d. Keeping tensors on the GPU

The WebGPU EP supports `Tensor.fromGpuBuffer()` for inputs and
`preferredOutputLocation: 'gpu-buffer'` for outputs, plus Graph Capture for
static-shaped models
([Using the WebGPU EP](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html)).
That is the mechanism for avoiding the readback §7 suspects of dominating the
current cost, and tfjs has no equivalent first-class API.

**One trap, from ORT's own docs:** *"The proxy worker cannot work with WebGPU
EP. This is because a GPU buffer is not transferable"*, and proxy workers
*"cannot work in a Content Security Policy (CSP) restricted environment"*
because they are created from a blob
([env flags and session options](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html)).
Both halves apply to us — blob Workers are already established as dead on
YouTube. **Never set `ort.env.wasm.proxy`.** Run ORT *inside* the Worker this
app already creates from its own same-origin synthetic URL; that path is fine
and needs no CSP allowance.

### 3e. Migration path from our tfjs graph models

- **tf2onnx is alive but fragile as a dependency.** Latest release **v1.17.0,
  2026-03-04**; last commit **2026-08-29**
  ([GitHub API](https://api.github.com/repos/onnx/tensorflow-onnx/releases/latest)).
  But the README says outright: *"We are currently **looking for a new
  maintainer** to help support and evolve the `tf2onnx` project."* It supports
  TF 2.x (tested tf-2.13+), Python 3.10–3.12, opsets 14–18
  ([tf2onnx README](https://github.com/onnx/tensorflow-onnx)).
- **The awkward part is direction.** tf2onnx converts SavedModel / frozen graph
  / TFLite → ONNX. Our models are *tfjs GraphModels* (`model.json` + `.bin`) —
  one hop further out. Practical routes: **(a)** go back to the original
  upstream artifact (MoveNet MultiPose and BlazeFace both exist upstream in
  TFLite/SavedModel form; faceres came from the MIT `vladmandic/human` model
  set), convert from there, and never round-trip through our own tfjs bundle;
  or **(b)** use an existing ONNX export — for MoveNet MultiPose one already
  exists on Hugging Face (`Xenova/movenet-multipose-lightning`), whose sizes
  are recorded in this repo's `docs/research/person-gate.md` as 19 MB fp32 /
  9.65 MB fp16 / 5.26 MB int8. **Re-read its licence before using it.**
- **Route (a) is the only honest one.** A tf → tfjs → back → onnx round trip
  accumulates two rounds of graph rewriting, and this codebase has already been
  bitten twice by a converted model that was "alive and still differentiating"
  and quietly wrong.

**The real cost is not conversion, it is validation.** The measured precedent
is in this repo: a uint8 requant of the gender model moved the sigmoid by up to
0.104 and **flipped 8 of 100 verdicts at `GENDER_IMAGE_MIN_SCORE`**, with a
descriptor cosine minimum of 0.5962 against a `MEM_SIM_CLEAR` of 0.60. A
runtime port is exactly the same class of change and must be gated on exactly
the same harness — `probe_faceres_parity.py` plus `app/gaze/bench/`,
byte-identical input tensors through both runtimes, all three heads compared —
before one verdict change is allowed to ship.

### 4b. NNAPI is deprecated, and there is no web-facing successor

Official NDK docs: *"**Warning:** NNAPI is deprecated. While you can continue
to use NNAPI, we expect the majority of devices in the future to use the CPU
backend, and therefore for performance critical workloads, we recommend
migrating to alternative solutions, for example the TF Lite GPU runtime"*, and
*"The API is available on all Android devices running Android 8.1 (API level
27) or higher, but was deprecated in Android 15"*
([developer.android.com/ndk/guides/neuralnetworks](https://developer.android.com/ndk/guides/neuralnetworks)).
The migration guide names two paths: **TensorFlow Lite in Google Play
Services** and the **TFLite GPU delegate**

([developers.google.com/edge/litert](https://developers.google.com/edge/litert)).

**All of those are native, app-level APIs with no JavaScript surface.**

which is the one genuine argument for §6's native bridge, and the reason it

**Timeline honesty:** no committed date exists for WebNN on Android or in
WebView. The desktop trial has already slipped twice and Android was dropped
from it with no re-entry milestone. Planning around WebNN before **2028** is
not defensible.

## 5. MediaPipe Tasks for Web, and LiteRT.js

### 5a. MediaPipe Tasks Vision — SHIPPING, actively maintained, but architecturally locked

`@mediapipe/tasks-vision` is at **1.0.1** with nightly `rc` builds published
daily (most recent `1.0.1-rc.20260901`, 2026-09-01)
([npm registry](https://registry.npmjs.org/@mediapipe/tasks-vision)); the
MediaPipe repo cut **v1.0.0 on 2026-07-28** and commits daily
([GitHub API](https://api.github.com/repos/google-ai-edge/mediapipe/releases/latest)).

**Runtime:** its own Emscripten C++/WASM build of the MediaPipe graph runner,
not tfjs. `baseOptions.delegate` is exactly `'CPU' | 'GPU'`
([`task_runner_options.d.ts`](https://github.com/google-ai-edge/mediapipe/blob/master/mediapipe/tasks/web/core/task_runner_options.d.ts)),
wired straight into TFLite's own delegates in
[`task_runner.ts`](https://github.com/google-ai-edge/mediapipe/blob/master/mediapipe/tasks/web/core/task_runner.ts):

```js
if (options.delegate === 'GPU') {
  acceleration.setGpu(new InferenceCalculatorOptions.Delegate.Gpu());
} else {
  acceleration.setTflite(new InferenceCalculatorOptions.Delegate.TfLite());
}
```

Per-frame GPU images move as **`WebGLTexture`** objects
([`vision_task_runner.ts`](https://github.com/google-ai-edge/mediapipe/blob/master/mediapipe/tasks/web/vision/core/vision_task_runner.ts)),
i.e. the Tasks-Vision "GPU" delegate is backed by **WebGL2, not WebGPU**. (A
separate `graph_runner_webgpu.ts` exists in
[`mediapipe/web/graph_runner`](https://github.com/google-ai-edge/mediapipe/tree/master/mediapipe/web/graph_runner)
but is the GenAI path, not this one.) *This conclusion is from source, not from
docs prose — Google does not state it in the rendered docs.*
**So MediaPipe Tasks is not a route to WebGPU.**

**Threading / isolation:** the shipped wasm directory for 1.0.1 contains only
`vision_wasm_internal` (SIMD) and `vision_wasm_nosimd_internal` — **no threaded
variant** — and
[`fileset_resolver.ts.template`](https://github.com/google-ai-edge/mediapipe/blob/master/mediapipe/tasks/web/core/fileset_resolver.ts.template)
picks between them purely by a `WebAssembly.validate()` SIMD probe, with no
mention of pthreads, `SharedArrayBuffer` or `crossOriginIsolated`. **Inference,
not a documented statement:** the shipped build is single-threaded and does not
need cross-origin isolation — which, given §2c, is actually a point in its
favour.

**Workers:** supported and recommended — the docs advise web workers to keep
`detect()` off the UI thread, and `task_runner.ts` accepts
`HTMLCanvasElement | OffscreenCanvas | null` and can create its own
OffscreenCanvas
([object detector web guide](https://developers.google.com/edge/mediapipe/solutions/vision/object_detector/web_js)).

**Licence:** Apache-2.0 for the framework and the npm package
([LICENSE](https://github.com/google-ai-edge/mediapipe/blob/master/LICENSE),
[npm](https://registry.npmjs.org/@mediapipe/tasks-vision/latest)); BlazeFace's

**Custom models: constrained, not open.** Each Task expects a `.tflite` with a

### 5b. LiteRT.js — the successor Google actually points at

`@litertjs/core` **2.5.3**, published **2026-07-17**, Apache-2.0
([npm registry](https://registry.npmjs.org/@litertjs/core)); repo
[google-ai-edge/LiteRT](https://github.com/google-ai-edge/LiteRT). Announced
2026-07-09 by the tfjs team's own authors (Ping Yu, Matthew Soulanille et al.)
([Google Developers Blog](https://developers.googleblog.com/litertjs-googles-high-performance-web-ai-inference/)).

**Backends: `wasm` (XNNPACK CPU), `webgpu`, `webnn`** — selected explicitly at
load:

```js
const model = await loadAndCompile('path_to_model.tflite', { accelerator: 'webgpu' });
```

([get started](https://developers.google.com/edge/litert/web/get_started)).
It runs **arbitrary `.tflite`** models, not a fixed task contract — a real
advantage over MediaPipe Tasks for our bespoke models. Documented limits: no
partial delegation, int32/float32 tensor I/O only, WASM memory ceiling on large
models, and some ops (e.g. `BROADCAST_TO`) needing model restructuring before
conversion. It ships a `@litertjs/tfjs-interop` package specifically so it can
be dropped into an existing tfjs pipeline — the migration story is designed for
exactly our situation.

**Two caveats before betting on it.** (1) The `webnn` accelerator *"requires
JSPI"* and WebNN is unavailable to us anyway (§4) — so on our targets LiteRT.js
is WebGPU-or-XNNPACK, same two horses as everyone else. (2) Its CPU backend is
described as XNNPACK "with multi-threading", which normally implies
`SharedArrayBuffer`; **its shipped wasm artifacts were not inspected for a
threaded/non-threaded split**, so whether it degrades gracefully without
cross-origin isolation is **unverified and must be checked before adoption** —
under §2c we will never have threads.

Its published numbers are vendor-blog, desktop, and unhelpful for us: "up to
3x" versus other web runtimes and "5-60x" GPU/NPU over CPU, on a **2024
MacBook Pro (M4)**, with the author's own caveat that "individual user
performance may vary based on local GPU capabilities, thermal throttling, and
browser driver optimization". **No Android numbers are published.**

## 6. Native inference via a Tauri command — the escape hatch, priced honestly

### 6a. Getting a frame OUT of the WebView — the bridge is worse than expected on Android

Three candidate channels, in order of how they actually perform:

**(1) Tauri's own `invoke` command bridge — JSON only on Android, confirmed.**
`tauri::ipc::InvokeBody` carries the documented note:

> **Android** — On Android, `InvokeBody::Raw` is not supported. The enum will
> always contain `InvokeBody::Json`. When targeting Android Devices, consider
> passing raw bytes as a base64 string.

([docs.rs `tauri::ipc::InvokeBody`, tauri 2.11.5](https://docs.rs/tauri/latest/tauri/ipc/enum.InvokeBody.html))
This is not a doc quirk; it is visible in wry's Android JNI signature, where
the IPC body crosses as a Java `String`:

```rust
pub unsafe fn ipc(mut env: JNIEnv, _: JClass, webview_id: JString, url: JString, body: JString)
```

([wry `src/android/binding.rs`](https://github.com/tauri-apps/wry/blob/dev/src/android/binding.rs))
Tauri's IPC concept doc confirms the framing: commands use a JSON-RPC protocol
and *"all arguments and return data must be serializable to JSON"*
([Tauri v2 IPC](https://v2.tauri.app/concept/inter-process-communication/)).
**So a frame sent through `invoke` on Android is base64 in a JS string, both
directions.**

**(2) The custom-protocol / `shouldInterceptRequest` route cannot carry a frame
at all.** `android.webkit.WebResourceRequest` exposes exactly six methods —
`getMethod()`, `getRequestHeaders()`, `getUrl()`, `hasGesture()`,
`isForMainFrame()`, `isRedirect()` — and **no body accessor**
([WebResourceRequest reference](https://developer.android.com/reference/android/webkit/WebResourceRequest)).
A POST to `https://tauri.localhost/frame` reaches native with its body
discarded. This channel is fine for *serving* bytes into the page (which is how
this app already delivers the gaze bundle and models) and useless for *sending*
them out.

**(3) `WebMessageListener` with an ArrayBuffer payload — the only real binary
channel, and it is a good one.** `androidx.webkit.WebMessageCompat` defines
`TYPE_ARRAY_BUFFER = 1` alongside `TYPE_STRING = 0`, a constructor
`WebMessageCompat(@NonNull byte[] arrayBuffer)` — *"Creates a WebMessage with
JavaScript ArrayBuffer payload"* — and `byte[] getArrayBuffer()`, gated by
`@RequiresFeature(name = WebViewFeature.WEB_MESSAGE_ARRAY_BUFFER)`
([WebMessageCompat reference](https://developer.android.com/reference/androidx/webkit/WebMessageCompat),
[WebViewFeature](https://developer.android.com/reference/androidx/webkit/WebViewFeature)).
Pair it with
`WebViewCompat.addWebMessageListener(webView, jsObjectName, allowedOriginRules, listener)`,
which is **origin-scoped**
([WebViewCompat reference](https://developer.android.com/reference/androidx/webkit/WebViewCompat)).

**And use that origin scoping, because the obvious alternative is a security
hole on these pages specifically.** `addJavascriptInterface` *"injects the
supplied Java object into **all frames** of the web page, including all the
iframes"*, and the docs warn: *"any frame could obtain the object name and call
methods on it. There is no way to tell the calling frame's origin from the app
side, so the app must not assume that the caller is trustworthy unless the app
can guarantee that no third party content is ever loaded into the WebView"*
([WebView reference](https://developer.android.com/reference/android/webkit/WebView)).
**Third-party content is the entire product.** YouTube's own JS would be able
to call an inference bridge exposed this way. `addWebMessageListener` with an
explicit origin allowlist is the correct primitive; `addJavascriptInterface` is
not.

One useful detail from the same page: *"JavaScript interacts with Java object
on a private, background thread of this WebView"* — bridge calls do **not** run
on the UI thread, so the bridge itself is not a jank source.

### 6b. Is the transfer cost prohibitive? First-principles arithmetic

No published benchmark exists for this exact pattern, so reason from sizes.
**The key move is to never send a frame — send a tensor.**

| Payload | Bytes |
|---|---|
| Raw 640x360 RGBA frame (his player's decode size) | 921,600 |
| MoveNet MultiPose input, 256x256x3 uint8 | **196,608** |
| A 224x224x3 uint8 faceres crop | 150,528 |
| Same 196,608 B, base64-encoded | 262,144 (then UTF-16 in JS: ~524,288 in memory) |

The page already resizes to model input with `createImageBitmap(video, crop,
{resize})`, so the honest per-pass payload is **~192 KB, not ~900 KB**, and at
this app's ~1.5 s verdict cadence that is ~128 KB/s — trivial. Even at 10 Hz it
is 1.9 MB/s, which an in-process JNI `byte[]` copy handles without noticing.

**The cost that does not go away is the readback.** To get pixels into an
`ArrayBuffer` at all you need `getImageData()` (2D canvas) or
`gl.readPixels()`, and that is precisely the GPU→CPU stall this repo has spent
rounds eliminating from the current pipeline. For a 256x256 buffer it is small
— hundreds of KB, typically single-digit ms — but it is a **synchronous
pipeline flush**, and it reintroduces the cost that §7 and §1 are both trying
to remove. WebCodecs does not rescue this: a `VideoFrame` can be handed to
WebGPU with zero copy (§7), but `copyTo()` into an `ArrayBuffer` is still a
readback.

**So the arithmetic does not kill the native bridge — the readback plus the
platform cost does.** Rough per-pass budget for the native route on Android:
resize (already paid) + readback ~2–8 ms + JNI/IPC ~1–3 ms + native TFLite GPU
delegate inference + return ~1 ms. Against a *plausible* native MoveNet cost of
tens of ms, that overhead is maybe 10–20% — acceptable **if** the native
inference really is an order of magnitude faster than the 500 ms being seen
today. That "if" is unmeasured and is the whole bet.

### 6c. On his actual device, the native win is the GPU delegate — there is no NPU to reach

This matters because "native = NPU" is the intuitive reason to take this
option, and on an Adreno 610 it is **false**.

- **Adreno 610 is a low/mid-tier 2020-class GPU with no separately-marketed
  NPU / Hexagon tensor accelerator.** The vendor NPU delegates now shipping —
  LiteRT's `CompiledModel` API with a **Qualcomm AI Engine Direct Delegate**
  on Maven Central, an Intel OpenVINO NPU path, with Google Pixel and Samsung
  System LSI delegates listed "coming soon"
  ([LiteRT NPU acceleration overview](https://developers.google.com/edge/litert/android/npu/overview))
  — target flagship-class silicon.
- ONNX Runtime's Qualcomm **QNN execution provider** makes the same point from
  the other side. Its HTP (NPU) backend has been validated on *"Qualcomm
  SC8280, SM8350, Snapdragon X SOC's"* — all flagship tier — and, decisively,
  **"The QNN HTP backend only supports quantized models"**
  ([QNN Execution Provider docs](https://onnxruntime.ai/docs/execution-providers/QNN-ExecutionProvider.html)).
  Its GPU backend, by contrast, accepts fp32/fp16 activations and weights
  natively.

**So the native route on his phone buys the TFLite/LiteRT GPU delegate
(OpenCL on Adreno) — a real thing, and the honest thing to compare against
500 ms — and nothing else.** It does not buy an NPU, and the one path that
would (QNN HTP) would simultaneously force the app back into the uint8
quantization it has already measured and rejected (§8). Two constraints that
independently rule out the same option are worth stating together.

*(Also worth noting on cost: ONNX Runtime Mobile supports custom stripped
builds — one documented example cuts the Android AAR from 24.4 MB to 7.5 MB
for a single-model build — so the native route's binary cost is tunable if it
is ever pursued: [ORT Mobile tutorial](https://onnxruntime.ai/docs/tutorials/mobile/).)*

**What is actually being bought, and what it costs.**

- **Bought:** access to the TFLite/LiteRT GPU delegate and to vendor NPU delegates — the only NPU route that exists (§4b) — plus a runtime Google actively maintains.
- **Cost:** two native implementations plus a third for iOS; model files shipped natively as well as (or instead of) in the bundle; and **the loss of a single verification surface**. Every probe, ring buffer, counter and bench in `spikes/gauntlet` and `app/gaze/bench` reads the page. Moving inference into Kotlin moves it out of reach of all of them, in a codebase whose entire safety culture is "measure it in the page, from the emitted bundle, on his device". **That is the strongest argument against this option and it is not a technical one.**

### 6d. Windows and iOS, briefly

- **Windows / WebView2:** the host is already Rust, so ONNX Runtime via the [`ort` crate](https://github.com/pykeio/ort) (MIT/Apache-2.0) with the DirectML EP is a genuinely small lift — no JNI, no Kotlin, and Tauri's `InvokeBody::Raw` restriction is **Android-only**, so raw bytes cross the desktop IPC without base64. But desktop is not where the pain is: WebView2 already has WebGPU (§1c) and desktop hardware already runs this pipeline acceptably. **Low value.**
- **iOS / WKWebView:** the equivalent is Core ML through a Tauri plugin, over the standard `WKUserContentController` / `WKScriptMessageHandler` bridge (JS `postMessage` → Swift handler → Core ML → post the result back); there is no direct JS access to Core ML, everything crosses through native code ([Apple Core ML docs](https://developer.apple.com/documentation/coreml)). Same frame-extraction problem, and iOS work is constrained to the cousin's visit window per the original handoff. **Do not open this front now**, but note that anything built here has to be *prepared* before that window, not discovered during it. Note only that WebGPU does not exist in Safari/WKWebView for our purposes — ORT's own matrix marks WebGPU ❌ on Safari iOS ([js/web/README.md](https://github.com/microsoft/onnxruntime/blob/main/js/web/README.md)) — so iOS will need *either* the native bridge or single-threaded WASM, whichever is chosen elsewhere.

## 7. Cheap wins inside the current TF.js WebGL stack

Ranked by expected value for this specific 500 ms number. Sources are the flag
registrations in
[`tfjs-backend-webgl/src/flags_webgl.ts`](https://github.com/tensorflow/tfjs/blob/master/tfjs-backend-webgl/src/flags_webgl.ts)
and the
[Platform and environment guide](https://www.tensorflow.org/js/guide/platform_environment)
unless stated.

| Lever | Default | What it buys | Verdict here |
|---|---|---|---|
| `WEBGL_USE_SHAPES_UNIFORMS` | **`false`** | Shapes as uniforms instead of shader literals, so one compiled program serves many input shapes | **Already in use** (shipped e668561). Keep. Biggest single win when input shapes vary, which is exactly this app's image path |
| `WEBGL_PACK` (+ ~9 sub-flags) | on whenever WebGL exists | 4 scalars per RGBA texel: quarter the texture memory and texel traffic | Already on. The per-op sub-flags (`WEBGL_PACK_DEPTHWISECONV`, `WEBGL_PACK_CONV2DTRANSPOSE`, …) exist so a regressing op can be excluded — worth an A/B on depthwise specifically, since MoveNet is depthwise-heavy |
| `WEBGL_FLUSH_THRESHOLD` | **`1` on mobile**, `-1` elsewhere | Forces a `gl.flush()` when >N ms have passed, so mobile drivers do not accumulate an unbounded command queue | Already active on his phone. | `WEBGL_DELETE_TEXTURE_THRESHOLD` | `-1` (never delete, always pool) | Texture reuse via `texture_manager.ts`'s free-pool, keyed by shape | Already optimal for a **fixed-shape** loop. **Risk in the other direction:** with many distinct crop sizes the free pool grows per shape and never releases. Worth reading `numFreeTextures` / `numBytesAllocated` on his phone |
| `WEBGL_CPU_FORWARD` | `true` | Tiny tensors run on CPU instead of paying GPU dispatch | Leave on unless chasing a pure-GPU pipeline |
| `CHECK_COMPUTATION_FOR_ERRORS` | follows `DEBUG` (`false`) | NaN/Inf checks — **forces a readback after every op** | Confirm it is off in the shipped bundle. If it were ever on, it alone would explain a 500 ms pass |
| `WEBGL_RENDER_FLOAT32_ENABLED` | device-probed | fp32 vs fp16 render targets; fp16 range is `[0.000000059605, 65504]` | Already measured on his device: Adreno 610 reports `HIGH_FLOAT precision 23` (true fp32) in both shaders. **Settled, do not re-open** |

Correct usage; keep the `finally` that clears it — left set, BlazeFace reports "no faces" and the drain *reveals* |

| `dataSync()` → `await data()` | — | *"it's important to use the asynchronous `x.data()` and `x.array()` methods over their synchronous counterparts ... to avoid blocking"* | Audit every remaining `dataSync()` in the player path. This is the readback class that dominates WebGL pipelines |

| **WebCodecs `VideoFrame` as a texture source** | — | See below | **The one genuinely new item in this table** |

**On `VideoFrame`, correcting a prior assumption in this repo.**
`docs/research/blur-architectures-2026-08-24.md` ground-truth item 2 implies a
`VideoFrame` is usable as a frame source generally. Precisely:

- **On WebGPU it is first-class and zero-copy.** The spec declares
  `required (HTMLVideoElement or VideoFrame) source;` on
  `GPUExternalTextureDescriptor`, and recommends driving it from
  `requestVideoFrameCallback()`; the external texture expires when the
  `VideoFrame` is closed
  ([WebGPU spec source](https://github.com/gpuweb/gpuweb/blob/main/spec/index.bs)).
- **On tfjs it is not accepted at all.** `tf.browser.fromPixels` and
  `fromPixelsAsync` take exactly
  `PixelData | ImageData | HTMLImageElement | HTMLCanvasElement | HTMLVideoElement | ImageBitmap`
  — `VideoFrame` is absent from both the type union and the runtime
  `instanceof` checks
  ([`tfjs-core/src/ops/browser.ts`](https://github.com/tensorflow/tfjs/blob/master/tfjs-core/src/ops/browser.ts)).

So a zero-copy `VideoFrame` path is **a reason to move to WebGPU** (tfjs-webgpu,
ORT WebGPU EP, or LiteRT.js), not something available on the current backend.
On WebGL the closest equivalent is the `HTMLVideoElement` overload of
`fromPixels`, which is already what this app does.

**The measurement that should precede all of the above:** confirm the WebGL
backend on his phone is hardware-accelerated and count shader compiles per
pass. This repo already has the harness for it — the WEBGL flag bench that
wraps `linkProgram` to count compiles (proven arch-independent in loop
2026-08-23). **If MoveNet is recompiling programs mid-session because crop
shapes vary, that is the 500 ms, and no runtime change fixes it.**

## 8. Quantization survivability

**tfjs: quantization is download-size only. Proven from source, not inferred.**
`tfjs-converter`'s `--quantize_uint8` / `--quantize_uint16` /
`--quantize_float16` compress the weight files; at *load* time
`decodeWeight()` in
[`tfjs-core/src/io/io_utils.ts`](https://github.com/tensorflow/tfjs/blob/master/tfjs-core/src/io/io_utils.ts)
expands every quantized tensor back into a `Float32Array`:

```ts
values = new Float32Array(quantizedArray.length);
for (let i = 0; i < quantizedArray.length; i++) {
  const v = quantizedArray[i];
  values[i] = v * quantization.scale + quantization.min;
}
```

The backend never sees an int8 tensor. The converter README's own framing —
*"1-byte affine quantization, i.e. `uint8` provides a 4x size reduction at the
cost of accuracy"* — mentions size and accuracy and, correctly, never mentions
speed
([tfjs-converter README](https://github.com/tensorflow/tfjs/blob/master/tfjs-converter/README.md)).

**This settles the question this repo has circled twice.** A tfjs uint8
requant is **all cost, no speed**: the affine round-trip permanently changes
the stored numbers (dequantization cannot recover what rounding destroyed),
and the graph still executes in float32. It is the exact mechanism behind
this repo's own measurements — a full-uint8 faceres requant moving the gender
sigmoid by up to 0.104 and flipping **17/100 decisions at
`GENDER_MIN_SCORE` and 8/100 at `GENDER_IMAGE_MIN_SCORE`**, and a full-uint8
MoveNet producing dead output on depthwise convs. **Given the stated policy —
download-only savings are not attractive — tfjs quantization is closed. Do not
retry it on this backend.**

**Where int8 *does* execute:**

- **ONNX Runtime WASM EP:** ORT compiles its native CPU engine to WebAssembly and its own README says the WASM backend supports *"full ONNX operator coverage, multi-threading, [ONNX Runtime Quantization](https://www.onnxruntime.ai/docs/how-to/quantization.html) as well as ONNX Runtime Mobile"* ([js/web/README.md](https://github.com/microsoft/onnxruntime/blob/main/js/web/README.md)), i.e. QDQ/QOperator int8 graphs are executed, not dequantized. **Caveat, flagged honestly: I could not find an ORT primary source stating explicitly that the *browser* WASM build runs true int8 SIMD kernels rather than falling back to float. Treat as likely-but-unconfirmed and measure it.**
- **ONNX Runtime WebGPU EP:** carries `DequantizeLinear`, `MatMulNBits` and `GatherBlockQuantized` ([webgpu-operators.md](https://github.com/microsoft/onnxruntime/blob/main/js/web/docs/webgpu-operators.md)) — real block-quantized matmul, but aimed at transformer weights, not at conv-heavy vision models. **Assume no int8 conv speedup on WebGPU.**
- **Qualcomm QNN HTP (NPU):** here int8 is not an optimisation, it is the **price of entry** — *"The QNN HTP backend only supports quantized models"*, requiring a float32→uint8/uint16 conversion with a calibration dataset before the NPU will run the graph at all; the QNN **GPU** backend accepts fp32/fp16 natively ([QNN EP docs](https://onnxruntime.ai/docs/execution-providers/QNN-ExecutionProvider.html)). Since §6c establishes that his device has no QNN-HTP-supported chipset anyway, this row is closed twice over.
- **Native TFLite / LiteRT:** the only place the win is documented as both size *and* speed — *dynamic range* quantization "4x smaller, 2x-3x speedup" (CPU) and *full integer* "4x smaller, 3x+ speedup" (CPU, Edge TPU, microcontrollers); float16 is "2x smaller, GPU acceleration" ([post-training quantization](https://developers.google.com/edge/litert/performance/post_training_quantization)). This is a genuine argument for §6's native route, and only for it.

**Accuracy cost, honestly:** Google's post-training-quantization page gives the
size/speed table above but **does not publish a per-model Top-1 accuracy
table** on the current page; it directs readers to verify accuracy themselves.
No MoveNet-specific or MediaPipe-specific int8 accuracy figure was found from
an official source. **The best accuracy data on this question anywhere is this
repo's own** — 8/100 verdict flips, 2 outright sign flips, 11 crossings of the
`isNullRead` band, and a descriptor cosine minimum of 0.5962 straddling
`MEM_SIM_CLEAR` 0.60. **Trust that over any published table**, and note that
one thing the MediaPipe table above does show is that int8 helps CPU and does
nothing for the GPU delegate (EfficientDet-Lite0: int8 29.31 ms CPU, no GPU row
at all).

**Practical rule, stated once: there is no runtime in this survey where
quantizing our gender model would both accelerate it *and* avoid the accuracy
cost already measured.** In tfjs it is dequantized before compute; on ORT
WebGPU the quantized kernels are transformer-shaped, not conv-shaped; on ORT
WASM it plausibly executes but is unconfirmed; on a Hexagon NPU it would be
mandatory — and that NPU is not on his device. Float16 remains the safe middle:
it halves bytes with a bounded, measured error, which is exactly the hybrid
uint8/f16 policy this repo already arrived at for MoveNet.

**Recommended sequence.**

1. **Probe** (hours): `navigator.gpu` + `adapter.info` in the Worker on his phone and in WebView2. Simultaneously, count shader compiles per MoveNet pass and audit `dataSync()` in the player path.
2. **If the 500 ms is shape churn or readbacks** → fix that on WebGL. Cheapest, safest, no verdict risk.
3. **If `navigator.gpu` exists** → A/B `tf.setBackend('webgpu')` behind a feature detect with WebGL fallback, gated on the parity harness. Ship it as a fast path, never as a requirement.
4. **If both of those leave the phone short** → port to ONNX Runtime Web, converting from upstream artifacts, with the parity harness as the gate.
5. **Native bridge only if 4 also falls short**, and re-read §6b's readback cost and §6's instrumentation loss before starting.

## 10. Dead ends — do not re-litigate

- **WASM threads on platform pages.** `SharedArrayBuffer` needs COOP+COEP response headers on YouTube's own document. Confirmed from spec, from tfjs's README, and from ORT's source (§2c). Both runtimes fall back to one thread silently and correctly.
- **WebNN, on any target we have.** Origin-trial tokens are origin-bound to origins we do not own; Android and Android WebView were explicitly dropped from the trial (§4).
- **Any NPU, from JavaScript.** NNAPI deprecated in Android 15; every replacement is a native API with no JS surface (§4b).
- **tfjs uint8/float16 quantization for speed.** Dequantized to `Float32Array` at load; pure download-size, with permanent accuracy loss, measured at 8/100 flipped verdicts in this repo (§8).
- **ORT's proxy worker.** Incompatible with the WebGPU EP (GPU buffers are not transferable) *and* with CSP-restricted pages (blob worker) — both halves apply to us (§3d).
- **`addJavascriptInterface` as an inference bridge.** Injected into all frames including iframes, with no way to identify the calling origin — on a third-party page, YouTube's own script could drive it (§6a).
- **The emulator, for any WebGPU question.** CPU adapters are blocklisted by `WebGPUBlocklistReason::CPUAdapter`; swiftshader has no hardware adapter to offer (§1a).
- **`developer.android.com/.../graphics/webgpu` as WebView evidence.** It documents the Jetpack `androidx.webgpu` native Kotlin bindings, not WebView (§1b).
- **`tf.browser.fromPixels(videoFrame)`.** `VideoFrame` is not in the accepted type union. Zero-copy `VideoFrame` is a WebGPU capability, not a tfjs one (§7).
