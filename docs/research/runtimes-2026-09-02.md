# Browser inference runtimes for a third-party WebView, 2026-09

Context this was written for: neural-net inference (MoveNet MultiPose person
detector, a custom faceres-derived gender/age model, NSFW classifier) runs
inside a Web Worker, inside **Android System WebView** (Tauri v2 Android
host) and **WebView2** (Tauri v2 Windows host), injected into third-party
pages (youtube.com, reddit.com, x.com, instagram.com) whose CSP and HTTP
response headers we do not control. Current stack: TensorFlow.js on the
`webgl` backend. Measured cost: ~500ms/MoveNet pass on an Adreno 610
(low/mid 2020 chipset), ~3000ms on an older device. This file surveys
whether a different runtime would be faster in 2026, without touching any
source code.

Every numbered section below matches the research brief. Sources are
inline; primary/official sources are preferred over blog posts.

---

## 1. WebGPU in Android WebView

**Chrome for Android (the browser app) is not the same ship vehicle as
Android System WebView**, and the evidence for the two diverges sharply.

- WebGPU shipped in the **Chrome browser** on Android in **Chrome 121**
  (Jan 2024), enabled by default for **Adreno (Qualcomm) and Mali (ARM)
  GPUs on Android 12+**, "the majority of the mobile market" at ship time,
  with other GPU vendors/older Android versions added later as testing
  allowed. [Chrome 121 WebGPU blog post](https://developer.chrome.com/blog/new-in-webgpu-121),
  [WebGPU release blog](https://developer.chrome.com/blog/webgpu-release).
- Imagination (PowerVR) GPUs were still being gated behind **Android 16+**
  as of the tracking bug's latest activity — evidence the Android rollout
  is GPU-vendor-by-GPU-vendor, not a single flag flip.
  [crbug 40287183 "Enable WebGPU on Android"](https://issues.chromium.org/issues/40287183)
- Chrome's own troubleshooting page states the hard version floor:
  **"WebGPU requires Chrome 113 or greater on ChromeOS, macOS, Windows and
  Chrome 121 or greater on Android."** It also documents that a
  per-GPU hardware blocklist exists and is inspectable at `chrome://gpu`,
  with `chrome://flags/#enable-unsafe-webgpu` and
  `chrome://flags/#ignore-gpu-blocklist` as escape hatches — flags a
  production WebView user obviously cannot set.
  [Troubleshooting tips](https://developer.chrome.com/docs/web-platform/webgpu/troubleshooting-tips)
- **Android System WebView is a distinct Chromium build target from Chrome
  for Android**, and the evidence we could find says it lags: a
  TensorFlow.js GitHub issue asking exactly "what WebView version supports
  the WebGPU backend" got no confirmed answer and reported WebView 96 (an
  old version) not supporting it.
  [tensorflow/tfjs#7910](https://github.com/tensorflow/tfjs/issues/7910)
  A generic browser-compat aggregator marks WebView as "supported" with no
  version number attached (i.e., not sourced from a dated release note the
  way the Chrome-for-Android entry is).
  [caniwebview.com WebGPU](https://caniwebview.com/features/web-feature-webgpu/)
  A separate, unrelated Android API also called "WebGPU" —
  `androidx.webgpu`, native Kotlin bindings to WebGPU for **native app
  rendering, not the `navigator.gpu` web API inside WebView** — exists and
  is easy to confuse with the web feature; it answers a different
  question entirely.
  [developer.android.com/.../graphics/webgpu](https://developer.android.com/develop/ui/views/graphics/webgpu)
- **Practical conclusion: do not assume WebGPU is available in Android
  System WebView just because Chrome for Android has it.** The two
  Chromium embeddings do not necessarily ship the same milestone or the
  same feature flags, and we found no dated, WebView-specific "WebGPU
  shipped in WebView M121" announcement equivalent to the Chrome-browser
  one. The only way to know for this app is to **feature-detect at
  runtime** (`navigator.gpu`, then `await navigator.gpu.requestAdapter()`
  — a null adapter means blocklisted or absent) on the actual Adreno 610
  device running our actual installed WebView build, and log the result.
- **WebView2 (Windows) is a much safer bet.** WebView2 tracks the Edge
  Chromium engine, and Edge shipped WebGPU on Windows (Direct3D 12)
  simultaneously with Chrome, from **Chrome/Edge 113 (April 2023)** — over
  a year before Android. [WebGPU — Wikipedia (timeline table)](https://en.wikipedia.org/wiki/WebGPU)
  We could not fetch a WebView2-specific "WebGPU shipped" release note
  (Microsoft's release-notes page is JS-rendered and didn't return body
  content to fetch), but because WebView2 always runs on top of an
  installed Edge/Chromium runtime that auto-updates, and desktop WebGPU
  has been GA since 2023, this is the highest-confidence "it just works"
  case in this whole survey — verify with the same `navigator.gpu`
  feature-detect rather than assuming.
- Speedup claim, not our hardware: Chrome's own WebGPU release announcement
  claims **"more than three times improvement in machine learning model
  inferences"** vs WebGL, without publishing the benchmark methodology.
  [WebGPU release blog](https://developer.chrome.com/blog/webgpu-release)
  A third-party MobileNetV2 microbenchmark found a smaller, more concrete
  number: **~30% faster steady-state** (9.5ms WebGPU vs 13.6ms WebGL per
  inference after warm-up) but **much slower first inference**
  (483ms WebGPU vs 1421ms WebGL — WebGPU's pipeline-creation cost is
  front-loaded differently than WebGL's shader compile).
  [ML in the browser with WebGPU — Joan León](https://joanleon.dev/en/webgpu-ml-browser/)
  Treat "3x" as a vendor upper bound and "~30% warm, worse cold" as the
  more credible number to plan around for a MobileNet-class model; MoveNet
  MultiPose is heavier and may scale differently in either direction —
  this needs an on-device A/B, not extrapolation.

## 2. TensorFlow.js backends

- **`webgl`** (current): mature, full kernel coverage, what we run today.
- **`webgpu`**: TensorFlow.js's own package README does not call it stable
  — it says the team is "committed to supporting it with rapid and
  continuous performance improvement" (future tense) and explicitly flags
  **missing kernels needed for gradient computation** (inference-only
  kernels are the priority; that's fine for us since we never train).
  No mobile-specific guidance or benchmark numbers are published in the
  README itself. [tfjs-backend-webgpu README](https://github.com/tensorflow/tfjs/tree/master/tfjs-backend-webgpu)
  Gate this on section 1: it is only reachable at all if WebGPU exists in
  our WebView.
- **`wasm`** (SIMD + threads): SIMD alone gives **1.7–4.5x over plain
  wasm**; multithreading adds **another 1.8–2.9x on top**, per Google's
  own benchmarks. [TF.js WASM SIMD+threads blog](https://blog.tensorflow.org/2020/09/supercharging-tensorflowjs-webassembly.html)
  **But the multithreaded number is very likely unreachable for us.**
  Threading requires `SharedArrayBuffer`, and `SharedArrayBuffer` requires
  the page to be **cross-origin isolated** — which requires the
  **top-level document's server** to send `Cross-Origin-Opener-Policy` and
  `Cross-Origin-Embedder-Policy` headers, and this isolation state
  propagates to every worker the page spawns. [MDN: SharedArrayBuffer security requirements](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer)
  youtube.com, reddit.com, x.com, and instagram.com do not set COEP for
  us and we cannot inject response headers from inside the page — we are
  a content script, not the origin server. **So `crossOriginIsolated` is
  false on every platform we run on, SharedArrayBuffer is unavailable, and
  we are pinned to the single-thread SIMD number: 1.7–4.5x over
  non-SIMD wasm, not the combined 3–13x the blog markets.** This is a
  structural ceiling, not a configuration bug — it cannot be fixed by us
  short of Chrome shipping isolation for extension-injected/WebView
  content in a way it does not today.
  (TF.js also had historical breakage tied to this exact
  requirement: [tfjs#4971](https://github.com/tensorflow/tfjs/issues/4971),
  [tfjs#6754](https://github.com/tensorflow/tfjs/issues/6754).)
- WASM is CPU-bound and has no path to the GPU; for a model like MoveNet
  MultiPose (higher FLOP count than MobileNet-class classifiers) it is
  very unlikely single-thread SIMD WASM beats WebGL on a phone GPU, even
  a weak one like Adreno 610. It is a credible fallback for the *gender/age*
  classifier crop passes (small, cheap) but not for the person detector.

## 3. ONNX Runtime Web

- WebGPU is **ONNX Runtime Web's default GPU execution provider** where
  available, and it claims out-of-the-box support on "latest versions of
  Chrome and Edge on Windows, macOS, **Android**, and ChromeOS," with
  Firefox behind a flag. [ORT Web WebGPU EP tutorial](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html)
  Read "Android" here the same way as section 1: this is almost certainly
  about the **Chrome browser** on Android, not Android System WebView —
  the same unverified gap applies.
- Maturity: ORT Web historically ran WebGPU through a JS-side shim called
  JSEP; a newer **native WebGPU EP built on Dawn (C++)** now coexists with
  it, with Microsoft's own tracking issue describing the two as expected
  to become mutually exclusive in a future change — i.e. **this is an
  actively-in-flux part of the runtime in 2026**, not a settled API
  surface. [Feature request / native WebGPU EP tracking issue #22077](https://github.com/microsoft/onnxruntime/issues/22077)
  Operator coverage is broad for modern architectures (Conv variants,
  MatMul/Gemm, normalization, attention, quantized matmul) — more than
  enough for MoveNet/MobileNet-class CNNs.
- WASM threads have the **identical `crossOriginIsolated`/SharedArrayBuffer
  gate as TF.js** — confirmed directly in ORT's own docs: "Only when the
  browser supports WebAssembly multi-threading and `crossOriginIsolated`
  mode is enabled, multi-threading will be enabled."
  [ORT Web env flags & session options](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html)
  So the same structural ceiling from section 2 applies to ORT Web's WASM
  EP inside a third-party page: single-thread SIMD only.
- One genuinely useful GPU-path feature ORT Web exposes that we do not
  currently use: `preferredOutputLocation`, which keeps intermediate/output
  tensors **on the GPU** instead of round-tripping to CPU between passes —
  directly relevant to us since our worker currently does readbacks (see
  section 7). Same doc as above.
- Migration path from TF.js: the runtime itself consumes ONNX, not TF.js
  graph models, so migrating means **re-exporting/converting all three
  models** (MoveNet-derived person detector, faceres-derived gender/age
  model, NSFW classifier) to ONNX — a nontrivial one-time cost, and for a
  model we've already hand-requantized (the gender model), re-deriving
  correctness on a different runtime's numerics is real work, not a
  format swap. We found no first-party "convert a TF.js *graph model*
  (not SavedModel) straight to ONNX" tool referenced in ORT's own web
  docs; the standard path goes through `tf2onnx` from a SavedModel/Keras
  model, which we may not still have for the two custom-trained/converted
  models.
- Bundle size: not disclosed in the docs we could reach; ORT Web ships
  multiple wasm binaries (simd/threaded/non-threaded × EPs) and is
  historically larger on disk than a single TF.js backend bundle, but we
  could not pull a concrete byte count from official sources this pass.

## 4. WebNN

**Verdict: not usable by us in 2026, full stop, on Android.**

- As of Chrome 146 (beta, 2026), WebNN is in an **Origin Trial**, and
  **Android is explicitly excluded from that origin trial** because the
  Android implementation is immature — **only CPU inference is
  implemented and shipped on Android today; GPU and NPU are planned but
  incomplete.** Estimated production/default-path timeline: **2027.**
  [Frontier Web APIs 2026 — WebNN section](https://www.utsubo.com/blog/frontier-web-apis-2026-production-ready),
  [Chrome 146 Beta WebNN origin trial — Phoronix](https://www.phoronix.com/news/Chrome-146-Beta)
- The API's own compatibility reference describes the **target**
  architecture once complete: on Android, CPU → TFLite+XNNPACK, GPU →
  TFLite GPU delegate (OpenCL), NPU → TFLite NNAPI delegate.
  [WebNN browser compatibility](https://webnn.io/en/api-reference/browser-compatibility/api)
  Two things to note: (a) this is the *design*, not what's shipped for
  Android today per the Phoronix/Utsubo sources above; (b) it routes
  through **NNAPI**, which Android itself has now deprecated (see
  section 6) — so even once WebNN's Android GPU/NPU paths land, they may
  be standing on a foundation Google is simultaneously walking away from
  natively.
- Core WebNN methods (`navigator.ml`, `MLContext`, `MLGraph`,
  `MLGraphBuilder`) shipped starting Chrome M112, with tensor ops in M129
  — but that's the desktop/general timeline; it does not imply Android
  parity, which the Origin Trial exclusion contradicts directly.
- **Decision for us: revisit WebNN no earlier than Chrome hits ~150 and
  Android leaves the origin-trial exclusion list; do not build against it
  now.**

## 5. MediaPipe Tasks for Web

- What it provides: a WASM (+ optional GPU delegate) runtime wrapping
  Google's own pretrained pipelines (Face Landmarker, Pose Landmarker,
  Object Detector, etc.), distributed as an npm package
  (`@mediapipe/tasks-vision`) or CDN bundle.
  [Face Landmarker for Web](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker/web_js)
- License: page content CC-BY-4.0, **code samples Apache 2.0** — compatible
  with this repo's MPL-2.0/MIT stance (same family we already use for
  Human/nsfwjs).
- **Custom models: effectively no, not the way we'd need.** MediaPipe's
  customization path is **MediaPipe Model Maker**, and Google's own docs
  carry a standing deprecation notice: **"MediaPipe Model Maker is still
  available, but is no longer actively maintained."** Model Maker also
  only *fine-tunes within a fixed task architecture* (Object Detector,
  Image Classifier, Gesture Recognizer, Text Classifier) — it is not a
  generic "bring your own architecture" path, and **Face/Pose Landmarker
  customization is not documented at all.**
  [MediaPipe custom model / Model Maker docs](https://developers.google.com/edge/mediapipe/solutions/customization/object_detector)
  We run a hand-picked MoveNet variant (our own hybrid uint8/f16 requant)
  and a custom faceres-derived gender/age head — neither fits inside
  MediaPipe's supported task/model families. **MediaPipe would mean
  replacing our detector and gender model with Google's own, not
  accelerating the ones we have** — an accuracy/behavior change, not a
  runtime swap, and out of scope for "make inference faster."
- We could not obtain latency numbers for MediaPipe's face/pose tasks on
  mid-range Android within this pass's tool budget; given the licensing
  and custom-model mismatch above, it wasn't worth spending further budget
  chasing timing data for a path we'd reject anyway.

## 6. Native inference via a Tauri command (the escape hatch)

This is the one place where **we** control the runtime, because Tauri
Android/Windows/iOS hosts are native code we already own.

**Android — TFLite/LiteRT:**
- TensorFlow Lite is now branded **LiteRT**, "Google's on-device framework
  for high-performance ML & GenAI deployment on edge platforms," built on
  the same foundation as TFLite (100,000+ apps use it today).
  [LiteRT overview](https://developers.google.com/edge/litert)
- **NNAPI is deprecated as of Android 15.** Google's own NDK docs:
  *"NNAPI is deprecated. While you can continue to use NNAPI, we expect
  the majority of devices in the future to use the CPU backend, and
  therefore for performance critical workloads, we recommend migrating to
  alternative solutions, for example the TF Lite GPU runtime."*
  [Android NDK NNAPI guide](https://developer.android.com/ndk/guides/neuralnetworks)
  Its replacement is not one universal delegate; it's **per-vendor NPU
  delegates plus the GPU delegate**: LiteRT ships a
  **CompiledModel API** with a **Qualcomm AI Engine Direct Delegate**
  already published on Maven Central (production distribution channel,
  not gated/early-access), an Intel OpenVINO NPU path, and **Google
  Pixel and Samsung System LSI delegates listed as "coming soon."**
  [LiteRT NPU acceleration overview](https://developers.google.com/edge/litert/android/npu/overview)
  Caveat for our exact hardware: Adreno 610 is a **low/mid 2020 GPU with
  no separately-marketed NPU/Hexagon tensor accelerator** — the vendor NPU
  delegate story above targets flagship-class Snapdragon/Tensor/Exynos
  silicon. On our target device the realistic native win is the **GPU
  delegate** (Adreno 610 via TFLite GPU/OpenCL), not an NPU delegate.
- **ONNX Runtime Mobile** is the alternative native path: Android via
  `onnxruntime-android` (Java/C/C++), with **NNAPI and XNNPACK** execution
  providers documented (i.e. still built against the API Google is
  deprecating, though it keeps working); custom stripped builds cut binary
  size dramatically (one cited example: AAR 24.4MB → 7.5MB for a
  ResNet50-only build). [ORT Mobile tutorial](https://onnxruntime.ai/docs/tutorials/mobile/)
  Qualcomm's own **QNN execution provider** targets Hexagon NPU (HTP)
  specifically, but its documented supported SoCs (SC8280, SM8350,
  Snapdragon X) are **flagship-tier, not Adreno-610-class** — the QNN HTP
  backend also **only accepts quantized (uint8/uint16) models**, so it
  would force us back into the accuracy-cost quantization tradeoff this
  repo already measured and rejected once (section 8).
  [ORT QNN Execution Provider docs](https://onnxruntime.ai/docs/execution-providers/QNN-ExecutionProvider.html)
- **Getting a video frame out of the WebView cheaply:** this is the make-
  or-break question, and the honest answer is "not for free."
  - `WebView.addJavascriptInterface` (the classic JS↔Kotlin bridge) only
    marshals primitives/Strings/collections — **no ArrayBuffer/byte[]
    support** — so a raw frame would have to go through **Base64**,
    which is the exact overhead we'd be trying to avoid (Base64 inflates
    payload ~33% and costs CPU to encode/decode on both sides).
  - The better-supported path is **`WebView.postWebMessage` +
    `MessagePort`**, which does structured-clone `ArrayBuffer` transfer
    between JS and native without Base64, on modern WebView. We could not
    pull a hard "since WebView version X" citation for ArrayBuffer-over-
    MessagePort in this pass, but the API predates 2026 by years and is
    the documented binary-transfer mechanism (`postMessage(data, '*',
    [buffer])` on the JS side).
  - Either path still requires **reading the frame off the GPU/video
    element on the JS side first** (canvas `getImageData` or
    `createImageBitmap`), which is the exact readback cost our own
    accuracy notes already flag as expensive relative to letting WebGL
    keep everything on-GPU (`fromPixels(video)` direct, no
    `getImageData`, per this repo's own Stage-1 zero-readback work).
    Round-tripping a downscaled frame (e.g. 256×256×3 uint8 = 196KB) as a
    raw `ArrayBuffer` over a MessagePort should be commodity-fast
    (single-digit ms, it's a structured-clone memory copy, not
    serialization) — **but this needs an on-device micro-benchmark, not
    an assumption**, before betting an architecture change on it.
  - **Net honest answer to "does frame-transfer cost eat the inference
    win": probably not for a downscaled 224–256px crop (which is already
    the size we feed today), but the JS-side pixel readback plus the
    Kotlin-side JNI/LiteRT call each cost something nonzero, and the
    entire premise of the native path is that the *inference* itself
    should be dramatically faster (real GPU delegate vs TF.js's shader-
    per-op WebGL translation layer) — we did not find a public number
    for "LiteRT GPU delegate MoveNet-MultiPose-equivalent latency on
    Adreno 610" to compare directly against our measured 500ms.**

**Windows — WebView2 + ONNX Runtime in Rust:** we already run a Rust host
process (Tauri). `ort` (the Rust ONNX Runtime binding) with the DirectML
or CUDA/CPU EP is a well-trodden path completely outside the WebView's
CSP/isolation constraints, and Rust↔JS transfer is the same
postMessage/IPC bridge Tauri already uses for everything else in this app.
This is lower-risk than the Android native path because we're not
fighting a JS-bridge binary-transfer limitation — Tauri's `invoke`/event
system already moves structured/binary payloads.

**iOS — WKWebView + Core ML:** the bridge pattern is
`WKUserContentController` / `WKScriptMessageHandler` (JS `postMessage` →
native Swift handler → run Core ML `.mlmodel` → post result back). Direct
JS access to Core ML does not exist; everything crosses through native
code. [Apple Core ML integration docs](https://developer.apple.com/documentation/coreml)
This project's own CLAUDE.md already scopes iOS work to the cousin's
visit window — any native-bridge redesign has to be prepared and testable
before that window, not discovered during it.

## 7. Cheap wins inside the current stack

These are available today, inside TF.js WebGL, with no runtime change —
several we already use per this repo's own history.

| Technique | What it buys | Status here |
|---|---|---|
| `WEBGL_USE_SHAPES_UNIFORMS` | Fewer shader recompiles when tensor shapes vary (uniforms instead of baking shape into the shader source) | **Already shipped** (this repo's own benchmark: gender shader compiles 223→98, per-batch recompiles 68→12, output bit-identical) |
| `WEBGL_PACK` | Packs 4 channels per RGBA texel — big win for conv/elementwise ops; on by default | Already default in tfjs-backend-webgl |
| `WEBGL_FLUSH_THRESHOLD` | Forces a manual `gl.flush()` after N ms so GL commands don't queue indefinitely; **defaults to 1ms on mobile specifically** in tfjs-backend-webgl's own flag file, `-1` (disabled) elsewhere — an existing mobile-specific mitigation, not a lever we need to touch further | Confirmed default in [tfjs-backend-webgl flags_webgl.ts](https://github.com/tensorflow/tfjs/blob/master/tfjs-backend-webgl/src/flags_webgl.ts) |
| `KHR_parallel_shader_compile` | Lets you poll `COMPLETION_STATUS_KHR` instead of blocking the thread on `gl.linkProgram`, so multiple shaders can compile concurrently on the driver side | **Already used** (this repo's warm-up: parallel compile pass before any real inference, `ENGINE_COMPILE_ONLY` flag) — [Khronos extension registry](https://registry.khronos.org/webgl/extensions/KHR_parallel_shader_compile/) |
| Avoiding GPU→CPU readbacks | `dataSync()`/`getImageData()` stall the GPU pipeline; staying in `fromPixels`/tensor space keeps everything on-GPU | Partially done (Stage-1 zero-readback for the player path per this repo's history); ORT Web's `preferredOutputLocation` (section 3) is the same idea for a different runtime |
| `createImageBitmap` with `resizeWidth/Height/Quality` | Decodes+downscales in one step, off the main thread if called from a Worker (`WorkerGlobalScope.createImageBitmap` exists) — avoids decoding a full-res image just to shrink it after | [MDN createImageBitmap](https://developer.mozilla.org/en-US/docs/Web/API/Window/createImageBitmap) — worth auditing whether every crop path already uses this vs. canvas-draw-then-read |
| `OffscreenCanvas` | Lets WebGL/2D canvas work happen inside the Worker itself, keeping the main thread free even for canvas-based preprocessing steps | [MDN OffscreenCanvas](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas) — relevant if any crop/resize step still touches a main-thread `<canvas>` before handing data to the worker |
| `VideoFrame` (WebCodecs) as a texture source | `GPUQueue.copyExternalImageToTexture()` explicitly accepts `VideoFrame` (confirmed — it's in the accepted-source list alongside `HTMLVideoElement`/`ImageBitmap`), letting the browser pick the most efficient zero-copy upload path per platform instead of us managing a canvas draw | [MDN copyExternalImageToTexture](https://developer.mozilla.org/en-US/docs/Web/API/GPUQueue/copyExternalImageToTexture) — WebGPU-only API, so gated on section 1's open question; `VideoFrame` itself is Baseline since Sept 2024 [MDN VideoFrame](https://developer.mozilla.org/en-US/docs/Web/API/VideoFrame) and usable as a WebGL `texImage2D` source too on Chromium, independent of WebGPU |

**Summary for section 7: most of the well-known WebGL mobile-perf levers
are already in this codebase** (parallel shader compile, shape uniforms,
zero-readback for the player path). The two most promising *unexplored*
items are (a) auditing every image-crop path to confirm it uses
`createImageBitmap({resize...})` instead of a canvas draw+read, and
(b) `VideoFrame`-as-texture-source once/if WebGPU is confirmed reachable.

## 8. Quantization that survives

- **TF.js's own converter documentation frames quantization purely as a
  transport optimization**: `tensorflowjs_converter`'s `--quantize_uint8`
  etc. flags exist to **"reduce the on-the-wire size of the weights
  through 16- or 8-bit quantization"** — the phrasing is about download
  size, not runtime speed, and we could not find a claim anywhere in
  TF.js's own docs that the WebGL backend executes quantized weights as
  integer math rather than dequantizing them back to float before compute.
  [tfjs-converter README](https://github.com/tensorflow/tfjs/tree/master/tfjs-converter)
  This matches this repo's own measured finding: a full-uint8 requant of
  the gender model **changed 8 of 100 verdicts** — i.e. real accuracy cost
  for a saving (download size only) that never showed up as faster
  inference, because the backend was dequantizing anyway. **Do not repeat
  that trade inside TF.js/WebGL** — there is no backend-side acceleration
  to justify the accuracy hit.
- **Where int8 quantization *does* accelerate compute (not just download)
  is a hardware-NPU execution provider**, and there it's often mandatory,
  not optional: Qualcomm's QNN **HTP backend "only supports quantized
  models"** — float32 has to be converted to uint8/uint16 first via a
  calibration-dataset workflow (QDQ nodes) before the Hexagon NPU will run
  it at all; the QNN **GPU** backend, by contrast, accepts float32/float16
  natively with no quantization required.
  [ORT QNN EP docs](https://onnxruntime.ai/docs/execution-providers/QNN-ExecutionProvider.html)
  So "does quantization pay off" is backend-specific: **yes if you're
  targeting a Hexagon NPU delegate (where it's the price of entry), no
  inside TF.js WebGL (dequantized before compute), and unclear/likely-no
  inside ONNX Runtime Web's WebGPU EP** — we found no explicit statement
  either way for ORT Web specifically; its general quantization docs
  discuss TensorRT (a native GPU path, not the web WebGPU EP) needing
  "hardware support to achieve better performance" for GPU quantization,
  which is consistent with "quantized-and-accelerated" being a
  server/native-GPU story more than a browser-WebGPU one today.
  [ORT quantization overview](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)
- **Practical rule for this app**: quantization is worth doing only on the
  one path where we'd actually reach a Hexagon-class NPU delegate (the
  native-bridge option in section 6), and even there our target device
  (Adreno 610) is not confirmed to have a QNN-HTP-supported chipset — so
  right now there is **no runtime in this survey where quantizing our
  gender model would both accelerate it and be free of the accuracy cost
  we already measured.** Float16 remains the safe middle ground we
  already use for some tensors (per this repo's own hybrid uint8/f16
  requant of MoveNet) — halves bytes with a bounded, measured error, no
  backend needs to treat it specially to get the download win, since
  browsers upload it and the GPU pipeline typically renders float16
  textures anyway on mobile (a pre-existing TF.js WebGL constraint, not a
  quantization choice).

| **Stay: TF.js WebGL** | 0 (baseline); maybe 10–20% from unfinished cheap wins in §7 (audit `createImageBitmap` resize usage) | Lowest — known quantity | Low (an afternoon of auditing crop paths) | Nothing new — just finish the audit already implied by our own shipped optimizations |
| **TF.js WebGPU** | ~30% warm-state per a third-party MobileNet microbenchmark, up to Chrome's marketed "3x" ceiling; **unknown/possibly 0 if unreachable** | **High** — the whole win is gated on a fact we could not confirm (does Android System WebView, not Chrome-for-Android, expose a hardware-accelerated `navigator.gpu` on our target OS/GPU) | Medium — mostly a backend string flip plus feature-detect/fallback code, gated on kernel-coverage gaps for inference ops we use | **Runtime feature-detection on the actual Adreno 610 device must return a non-null GPU adapter from `navigator.gpu.requestAdapter()` inside our actual WebView build.** This is a five-minute on-device check that should happen before any other WebGPU work. WebView2/Windows is much more likely to already work (Edge 113+, 2023) — test that side first, it's nearly free. |
| **ONNX Runtime Web** | Similar ceiling to TF.js WebGPU when WebGPU is reachable (same underlying GPU API); WASM path has the identical SIMD-only ceiling as TF.js (no COI in a 3p page either way) | Medium-high — runtime is itself mid-transition (JSEP → native Dawn EP), plus a real model-conversion project (3 custom models, one already hand-requantized) | High — full migration of 3 models + revalidating gender-model accuracy on new numerics | Only worth it if TF.js's WebGPU backend specifically has a kernel gap or bug blocking us that ORT Web's more complete op coverage would fix — not a general "faster" bet by itself |
| **Native bridge (Tauri→Kotlin LiteRT / Rust `ort` on Windows)** | Potentially the largest — real GPU delegate compute instead of WebGL-as-a-shader-compiler, no WebView feature gate at all | Medium — engineering complexity (JNI/LiteRT wiring, binary bridge, per-platform code), but *not* gated on an uncertain browser feature the way WebGPU is | Highest — new native code path per platform (Kotlin+LiteRT, Rust+`ort`+DirectML, Swift+CoreML), a binary frame-transfer channel, and it still needs the JS-side pixel readback our own notes already flag as non-free | **An on-device micro-benchmark showing frame-transfer (WebView pixel readback → `ArrayBuffer` → native) costs low-single-digit ms for a 224–256px crop, and a LiteRT GPU-delegate MoveNet-class benchmark that beats our measured 500ms WebGL number by enough to justify three platform-specific implementations.** Windows is the cheapest of the three to prototype (Rust already owns the host process) — start there if this path is pursued at all. |

**Bottom line:** nothing in this survey is a free win. The single highest-
leverage, lowest-cost next step is not adopting a new runtime — it's
**running `navigator.gpu.requestAdapter()` inside the actual Android
WebView build on the Adreno 610 device (and separately inside WebView2 on
Windows) and logging the result**, because every other row in the table
above is either gated on that answer or strictly more expensive than it.
