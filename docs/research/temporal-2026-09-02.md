# The temporal / association layer — design, 2026-09-02

Research + design deliverable. **No source was changed.** Every number
with a table around it was produced by running this repo's own bench
against `Z:/tamescroll-corpus` on 2026-09-02; every number quoted from
elsewhere names its source. Where a claim is unmeasured it says so and
names the experiment that would settle it.

Companion documents written the same day cover the neighbouring
questions and are deliberately not repeated here:
`docs/research/person-detect-2026-09-02.md` (box-only detectors to
replace MoveNet), `docs/research/models-2026-09-02.md`,
`docs/research/video-tracking.md` (the earlier generic MOT survey), and
`docs/plan-engine-v3.md` (the whole-engine plan). This document is only
about **when a verdict is made, which track it lands on, and what the
track does between verdicts.**

---

## 0. The answer, up front

The brief said the correct verdict exists but does not reach the right
track soon enough to matter. That is right, and the mechanism turned out
to be narrower and cheaper to fix than the brief assumed.

**`newTrack()` never applies a verdict. It hardcodes `state: "blurred"`
and only *banks* `clearStreak: 1`.** The entire clear ladder — the
streak, the 1.5s hold, and `obs.instant` (the single-read escape at
score >= 0.80), and the identity-memory grant which is expressed
*as* `obs.instant` — all of it lives in `matchedStep`, which by
definition only runs on a track that already existed. So a man whose
very first read on a new track is a confident, same-gender, adult,
signal-carrying clear is covered anyway, and stays covered until a
*later* verdict associates to the *same* id.

`bench/churn.mjs`, re-run today: over the 479 frames in which a face
this corpus labels MAN is covered, the covering track id changes **260
times across 163 distinct ids**, and a single id keeps covering him for
a median of **1 frame** (mean 1.8 frames = 0.9s) against a verdict
interval of 1.5s. The ladder needs two verdicts on one id. The id does
not survive one.

That is why every threshold swept this month moved 1-3 seconds. They
were all tuning a ladder the population never climbs.

Measured today, man mode, his regime (1.5s/verdict, coast, scene gate,
null-mint hold, adjacency clamp, inert-no-signal, identity memory — the
shipped arm):

| arm | EXPOSURE | FALSE COVER | PHANTOM |
|---|---|---|---|
| B0 shipped — birth always blurred | 81.0s | **216.5s** | 144.0s |
| **B1 — birth clears on `obs.instant`** | **83.5s** | **110.0s** | **122.5s** |
| B2 — birth clears on any certain clear | 88.0s | 63.5s | 108.0s |

Woman mode, same arms: 85.0/223.5/141.5 -> **89.5/153.5/128.5** (B1) ->
90.5/140.5/125.5 (B2).

**B1 buys 106.5s of false cover and 21.5s of phantom for 2.5s of
exposure, in both modes, and it is a five-line change to one function.**
It is the cheapest high-value change available and it is what I would
build first.

The clock is the second lever and it composes with the first (§4.3).
The cheap inter-frame tracker is the third, and — this is the part the
brief gets wrong — **it cannot buy the exposure number**; see §3.2.

## 1. Ground truth: what the code actually does today

Read before designing. Line references are HEAD at the time of writing.

### 1.1 The three rates that exist on paper

`init-entry.js:3229 sampleOnce()` runs on an interval and gates two
kinds of pass:

* **position pass** — `effInterval = min(POSITION_MAX_INTERVAL_MS 1000,
  max(sampleInterval, lastPassMs * POSITION_DUTY 2))`. Calls
  `runPass(withFaces=false)`, which still runs **MoveNet**, and returns
  `persons.map(p => ({box: p, positionOnly: true}))` (line 3554).
* **verdict pass** — `effZoom = min(VERDICT_MAX_INTERVAL_MS 2000,
  max(ZOOM_INTERVAL_MS 400, lastVerdictMs * VERDICT_DUTY 4))`. MoveNet +
  BlazeFace full-frame + up to `ZOOM_MAX_PERSONS_WORKER 6` faceres
  crops.
* **render loop** — `video-region.mjs` rAF at ~30-60Hz, pure
  interpolation (`lerpRect`, velocity extrapolation, `MOVE_DEADBAND`).
  It carries **no evidence**; it re-draws what the tracker last said.

The scene gate (`gateTick`, `GATE_INTERVAL_MS 100`) is a fourth,
independent 10Hz rate that only draws a 16x16 canvas and thresholds a
mean-abs luma delta.

### 1.2 The state each rate carries

`updatePersonTracks(tracks, observations, dtMs, hold)`:

* association: all-pairs IoU, gated by `PTRACK_IOU_MIN 0.2` and by
  `sizeCompatible` (`PTRACK_SIZE_RATIO_MAX 6` on area); pairs sorted by
  IoU descending, greedy claim. **Not Hungarian.** No motion cost, no
  appearance cost in the association itself.
* matched -> `matchedStep`: asymmetric EMA on the box
  (`PTRACK_EMA_ALPHA 0.6` grow, `0.2` shrink on a source flip or a
  position-only obs), then the verdict branch.
* unmatched track -> `coastStep`: constant-velocity extrapolation with
  velocity decayed 0.7 per step; dies past `blurredCoastMs` /
  `clearedCoastMs` / `cutCoastMs`, all rescaled by
  `setVerdictCadence(effZoom)` to ~2.5 verdict intervals, capped at
  `max(PTRACK_MAX_COAST_MS 2000, 2 * effZoom)`.
* unmatched observation -> `newTrack` (see §2).

Verdict branch, in order: identity SNAP on `sameSim < IDENT_SIM_MIN
0.15`; flag-certain -> instant blur; abstain -> demote after 2;
clear-certain -> `clearMs += verdictDt`, `clearStreak += 1`, clear if
`obs.instant || clearMs >= CLEAR_HOLD_MS 1500 || clearStreak >=
CLEAR_STREAK_N 2`; anything else -> `clearMs` decays by
`CLEAR_DECAY 0.5`. `CLEARED_TTL_MS 5000` demotes a clear nobody
re-confirms.

### 1.3 The two structural defects this design has to fix

**(a) The verdict is not applied at birth.** `person-track.mjs:1818
newTrack()` — `state: "blurred"` is a literal. `obs.instant` is not
read. `identity-memory.mjs` exists explicitly because "an identity
outlives the track that carries it" and its header quotes the churn
measurement above — and the way the app expresses a memory grant is
`obsOut.instant = true` (`init-entry.js:3112-3132`), which `newTrack`
ignores. **The identity memory is structurally unable to act on the
exact event it was written for.** That is not a tuning question.

**(b) The position pass does not exist on his hardware.** A position
pass is MoveNet and nothing else. MoveNet admits **nobody** on his
footage — twelve slots `n:0`, measured on his phone in loops 27, 35, 36
and 37 — so a position pass produces an **empty observation array**,
every track coasts, and the pass cost ~500ms of a ~795ms budget
(loop 27-28: passP50 504ms) to produce nothing. The two-rate split is
real in the source and absent on the device. This is also why
`bench/matrix.mjs`'s `coast` mode is the honest model of his regime and
`position` mode is not.

## 2. Finding 1 — apply the verdict at birth (the first thing to build)

### 2.1 The change

In `newTrack(obs)`, replace the literal with a guarded expression, and
only that:

```
state: (!obs.flagged && obs.instant) ? 'cleared' : 'blurred',
```

Nothing else in the object changes. `clearStreak`, `lastVerdict`,
`weakStreak` and `desc` are already seeded correctly.

### 2.2 Why this is safe, in the terms this repo uses

* **Unknown still covers.** The default remains `'blurred'`. The only
  way out is `!flagged && instant`, which requires: a *directed* read
  (`gender === 'male'|'female'`), the *same* gender as the user,
  `isAdultRead` true, `isNullRead` false, and
  `score >= instantClearScoreFor(gender)` — **0.80 male / 0.70 female**.
  Every one of those is already the bar the shipped `matchedStep` uses
  to clear a *matched* track on a single read. This adds no new
  authority; it removes an arbitrary dependence on whether the same id
  happened to survive the previous pass.
* **The error direction is bounded and priced.** The worst case is a
  woman misread same-gender at >= 0.80 with `childP < 0.25` and
  `nm >= 5`, cleared one verdict earlier than before. That is exactly
  the cost `gender-verdict.mjs:295` already argues and accepts for
  `GENDER_INSTANT_CLEAR`; this change extends its reach, it does not
  lower its bar. The corpus prices the whole of it at **+2.5s man /
  +4.5s woman**.
* **It restores the identity memory to usefulness** rather than adding a
  new mechanism. `mem-audit.mjs` already audited the memory at 359
  firings in man mode with **zero reachable wrong firings**; every one
  of those firings on a *birth* is currently discarded.

### 2.3 Why B2 is not the recommendation

B2 (clear at birth on any `certain` same-gender read, i.e. score >= the
`GENDER_CLEAR_SCORE` 0.45 bar) is better on the score — 63.5s false
cover — and I am refusing it. Its exposure cost is not merely larger, it
**grows with the clock**: at 1.5s/verdict B2 costs +7.0s of exposure
against B1's +2.5s; at 0.5s/verdict it costs **+9.0s against B1's
+1.5s** (§4.3 table). A change whose safety cost scales up as the rest
of the plan makes the pipeline faster is the wrong shape. B1's does not.

B2 is worth keeping as a *measured* upper bound on what this lever is
worth, and as the arm to re-run if the descriptor ever separates well
enough to gate a birth clear on identity rather than on score alone.

### 2.4 What would kill it

* Per-window attribution of the +2.5s. If the extra exposure is
  concentrated in one or two windows it may be a single subject whose
  read is confidently wrong, which is a different (and worse) story than
  a diffuse cost. **Not yet run** — see §10, E1.
* A render check. The score cannot see a patch that lifts for 1.5s and
  comes back. `bench/export-frames.mjs` on the windows whose exposure
  moved, B0 against B1, judged by eye.

## 3. Decoupling position from identity, properly

### 3.1 The scheme

Four rates, with an explicit statement of what state each owns. The
change from today is that **rate 2 stops being MoveNet** and **rate 3
gains a retroactive step**.

| rate | period | work | owns |
|---|---|---|---|
| **R0 render** | rAF, 30-60Hz | interpolate + draw | nothing. Pure function of R1/R3 state. No evidence, no decisions. |
| **R1 position** | 100ms (rides the existing `gateTick`) | one small luma readback; global-motion estimate; per-track box propagation | `box`, `vx/vy`, `missMs`. **Never** `state`, `clearMs`, `clearStreak`, `desc`. |
| **R2 scene** | 100ms, same readback | cut / static / motion classification | `epoch`, and the demotion decision |
| **R3 verdict** | 300ms-1.5s | face detect + faceres crops | `state`, evidence, `desc`, box correction |

R1 and R2 share **one** canvas readback per tick. Today `gateTick`
already does `drawImage(video, 0,0,16,16)` + `getImageData` at 10Hz; R1
needs a larger plane (§5) but not a second readback. That matters: on
this hardware the readback stall, not the pixel count, is the cost.

The critical invariant, stated so a future round cannot quietly break
it: **R1 may move a patch and may keep a track alive; it may never
change what a patch means.** A position update must not create a track,
must not clear one, and must not revoke a clear. This is the rule the
1068-1070 person-skip violated (a skipped pass reported an empty person
list, which reached `emptyFrame` and `wipeIfEmpty` and *erased* a
covered woman) and it is why that shipped an exposure and was reverted.

### 3.2 The honest limit — a position tracker cannot buy the exposure number

The brief reads the 81.0 -> 43.5 -> 8.0s cadence curve as evidence that
timing is worth 73 seconds. It is, but not in a way a tracker can
collect. `bench/cadence-ab.mjs` thins the corpus with `mode: 'coast'`,
which removes the **observation** entirely — so the 73s is the value of
*detecting and reading faces more often*, not of knowing where a known
face moved to. A flow tracker has nothing to say about a person who has
not been detected yet.

So the levers split cleanly, and conflating them is the main way this
design could waste a month:

* **Exposure** is bought by **verdict rate** — i.e. by making a pass
  cheaper (drop MoveNet, §3.3) or by an event trigger (§7.3). Nothing
  else moves it.
* **False cover** is bought by **birth-time verdict application** (§2)
  and by **track survival** — which is what a position tracker buys,
  because a track that survives is a track whose clear survives.
* **Phantom** is *spent* by both, and is the one number that gets worse
  (§4.3).

### 3.3 The pass that has to get cheaper first

MoveNet is 500ms of a 795ms verdict on his phone and contributes, in his
regime, essentially nothing. After 1078 made the ghost gate a **counter
rather than a refusal** (owner ruling, "she needs to be blurred"), the
only surviving consumers of `persons`/`noHumanShape` are:

1. body boxes — **empty on his footage, every window, every loop since
   27**;
2. `noShape`, which now gates only diagnostic counters, the composite
   frame, and one narrow suppression: whether a face may contribute
   `faceHeight * 3` to `passMaxBoxH` and thereby arm `wipeIfEmpty`'s
   one-pass `big` shortcut (`init-entry.js:3792-3805`);
3. `emptyFrame = persons.length === 0 && faces.length === 0` — where
   `faces.length` already dominates.

Dropping it roughly triples the verdict rate, which is where the 73s
lives. **The reason 1068-1070 failed is not a reason not to do this.**
That build modelled a skipped pass as a *boolean*: `persons = []` plus a
*held* `noHumanShape`, so a pass the model never ran was indistinguishable
from a pass that ran and found nobody, and `wipeIfEmpty` erased people.
The fix is a three-state, not a held flag:

```
personEvidence: 'found' | 'empty' | 'absent'
```

with `'absent'` making every MoveNet-derived predicate **undefined**, and
every consumer taking its fail-toward-covering default on undefined:
`emptyFrame` false, `passMaxBoxH` contribution suppressed, `noShape`
false. A test must assert that `'absent'` can never produce
`emptyFrame === true`. That is the whole difference between this and the
build that shipped an exposure.

Which detector (if any) replaces MoveNet is `person-detect-2026-09-02.md`'s
question, not this document's. What this document asserts is only that
**the verdict clock is the exposure lever, and the person model is what
is holding the clock down.**

### 3.4 Retroactive verdict attachment

A verdict pass is issued against frame `t0` and lands at `t0 + L`, where
L is 300-900ms on his phone and up to 3.9s on the older device. Today the
observation is associated against tracks whose boxes have been coasted
forward to `t1`, so the IoU is computed between a box measured at `t0`
and a prediction for `t1` — a mismatch that grows with L and is
attributed to nobody. On a `passEpoch` change it is simply dropped
(`passDropped` 29 of 39 cuts in one 90s window).

The fix is OC-SORT's **Observation-centric Re-Update** (Cao et al.,
CVPR 2023, arXiv:2203.14360), which is a genuinely good structural match
here and needs no code from their repo (MIT, but clean-room from the
paper regardless — note their LICENSE still carries ByteTrack's
copyright line, which is a reason to read the paper and not the file):

1. Keep, per track, a small ring of `{t, box}` from R1 — this is free,
   R1 is already producing them.
2. When a verdict for `t0` lands, associate it against the track's
   **stored box at `t0`**, not its current box. That is what the ring is
   for.
3. On a match, build the virtual trajectory between the previous real
   observation and this one, replay the box/velocity update along it,
   and **then** re-propagate forward to `now` using the R1 boxes already
   recorded. The verdict lands on the right track, and the track's
   velocity is anchored to two real measurements rather than to
   accumulated extrapolation.

OC-SORT's **observation-centric momentum** (OCM) is the part I would
*not* take. Its motivation is that frame-to-frame velocity at 30Hz is
dominated by detector jitter (their own `1/dt^2` argument, ~2px real
displacement on MOT17); our real observations are already ~1s apart, so
we are already in the regime OCM is reaching *for*. The general principle
— prefer velocity computed from two verified observations over velocity
accumulated through many unverified predictions — is worth writing into
the code as a comment and is exactly what step 3 does.

**Should a verdict apply backwards over the frames since the
observation?** For the *box*, yes — that is step 3, and it is free
because those frames are already drawn and gone. For the *state*, no,
and the asymmetry matters: a clear that arrives late must apply from
*now*, never retroactively, because there is no such thing as
retroactively un-blurring a frame the user already saw; whereas a flag
that arrives late is already applied at `now` and applying it earlier is
meaningless. So the rule is: **boxes are re-fitted backwards, verdicts
only ever apply forwards.** That keeps the safety direction trivially
intact and avoids a whole class of bug where a late clear is credited
with time it did not have.

## 4. The clock

### 4.1 What buying it costs

The number the brief did not quote, and it is the one that will cause
the owner's next complaint. From `cadence-ab.mjs`, man mode:

| verdict cadence | EXPOSURE | FALSE COVER | PHANTOM |
|---|---|---|---|
| 1.5s (his regime) | 81.0s | 216.5s | **144.0s** |
| 1.0s | 43.5s | 192.5s | **160.0s** |
| 0.5s | 8.0s | 156.0s | **260.5s** |

**Phantom rises 81% as the clock triples.** The mechanism is not subtle:
phantom is dominated by patch *mints*, and a mint happens on a verdict.
Three times the verdicts, three times the opportunities for a graphic
that reads as a face to be born a patch — which is the owner's "random
blur marks here and there" verbatim, and it is the complaint that was
accepted as the cost of the 1078 ghost-gate ruling.

So the clock is not free and must not be shipped alone. It has to ride
with a mint guard that scales: the bounded null-mint hold
(`nullDropped` / `nullMintedHeld`, already shipped) and
`NULL_MINT_NM_FLOOR`, both of which act *per birth* and therefore
tighten automatically as births multiply. Whether that is enough is
**unmeasured** — see §10, E4.

### 4.2 The one number that decides whether the clock is affordable

Everything above is corpus arithmetic. On his device the question is
what a verdict pass costs once MoveNet is gone. The measurement
(§10, E3) is a device A/B on the built APK reading `stage` marks from
the existing ring: `persons`, `fullFaces`, `crops`, `end`. If a
MoveNet-free verdict is ~300ms, `effZoom = max(400, 300*4) = 1200ms` and
the clock lands near the 1.0s row. If the crop stage dominates instead,
the lever is `ZOOM_MAX_PERSONS` and the rotation cursor, not the person
model, and this whole section is re-priced.

### 4.3 The two levers compose

Birth-clear crossed with cadence, man mode, measured today:

| cadence | arm | EXPOSURE | FALSE COVER | PHANTOM |
|---|---|---|---|---|
| 1.5s | B0 shipped | 81.0s | 216.5s | 144.0s |
| 1.5s | **B1** | 83.5s | 110.0s | 122.5s |
| 1.5s | B2 | 88.0s | 63.5s | 108.0s |
| 1.0s | B0 | 43.5s | 192.5s | 160.0s |
| 1.0s | **B1** | 44.0s | 99.5s | 137.0s |
| 1.0s | B2 | 46.5s | 63.0s | 126.0s |
| 0.5s | B0 | 8.0s | 156.0s | 260.5s |
| 0.5s | **B1** | **9.5s** | **96.0s** | 245.5s |
| 0.5s | B2 | 17.0s | 74.0s | 229.0s |

Read three things off it:

1. **B1 and the clock are orthogonal.** B1 removes ~100s of false cover
   at every cadence; the clock removes ~72s of exposure independently.
   Together: 81.0/216.5/144.0 -> **9.5/96.0/245.5**.
2. **B1 makes the clock cheaper on phantom too** (-15s at 0.5s), because
   a track that clears at birth is a patch that stops being drawn.
3. **B2's exposure cost scales with the clock and B1's does not**
   (+9.0s vs +1.5s at 0.5s). §2.3.

### 4.4 Interaction with the existing scroll and budget gates

`SCROLL_INTERVAL_MS 500` and `overBudget()` both already suppress
verdicts. Both are correct and should stay: they defer the *clearing*
half of the work, which is the safe direction. But if the clock speeds
up, `INPUT_YIELD_MAX 3` becomes a *smaller* absolute stall (3 skipped
passes at 300ms is 900ms, versus 3 at 1500ms being 4.5s — it gets
better, not worse). No change proposed.

## 5. A cheap inter-frame tracker

### 5.1 What it is for, precisely

Not exposure (§3.2). Its job is to make **R1 exist on his hardware**, so
that:

* a track is refreshed rather than coasted, so `missMs` resets and it
  survives to the next verdict — attacking churn at the source;
* the box at verdict time is a measurement rather than a 1.5s
  extrapolation, so IoU association lands on the right track;
* the patch tracks the subject between verdicts instead of drifting on a
  decaying velocity (`coastStep` decays v by 0.7 per step — a coast is
  an admission that we do not know).

### 5.2 The survey

All licences below were verified against the actual LICENSE file or
package metadata during this research pass.

| candidate | cost at 256x144, 1-4 boxes | drift / failure | permissive impl |
|---|---|---|---|
| **Pyramidal Lucas-Kanade (KLT)** | ~20-40 features/box, 15-21px window, 2-3 levels -> a few 10^5 MACs; low single-digit ms in plain JS | brightness-constancy breaks on lighting change and out-of-plane rotation; features die off and need re-seeding; loses lock past the top-level search radius | **jsfeat** (`inspirit/jsfeat`, **MIT**, `jsfeat.optical_flow_lk`, last push 2022-04) and **speedy-vision** (`alemart/speedy-vision`, **Apache-2.0**, WebGL2 `Speedy.Keypoint.Tracker.LK()`, last push 2025-06) |
| **NCC template match**, 24x24 template, +/-16px | 1089 windows x 576 MACs ~= 627K MACs/box with integral images for the local stats (the cross term cannot be reduced without an FFT); ~=2.5M MACs/frame for 4 boxes, ~75M MAC/s at 30Hz | no adaptation — degrades on any appearance change; no scale unless multi-scaled | none needed — ~30 lines, zero dependency, zero licence risk |
| **MOSSE** (Bolme 2010) | best big-O: 3 FFTs of a 64x64 patch ~= 150-200K ops/box | drifts on scale change and fast motion; PSR is the only self-diagnostic | `auduno/mosse` **MIT**, but 2017-stale and scoped to face/eye patches with MUCT-trained filters — you would reuse the FFT plumbing, not the filters |
| **KCF / CSRT / DSST** | KCF feasible with raw-pixel features; CSRT is not | boundary effects on fast motion; no loss signal | `opencv_contrib` is Apache-2.0 **but the `tracking` module is not in the stock opencv.js build** — needs a from-source contrib build with documented breakage (`opencv/opencv_contrib#1036`). Deprioritise. |
| **nano-Siamese (NanoTrack / LightTrack)** | low-to-mid tens of ms per call on Adreno 610 through tfjs-webgl, realistically | robust to appearance/scale, but can lock onto a distractor — i.e. **onto the wrong person**, which is the failure we are trying to remove | `HonglinChu/NanoTrack` code **Apache-2.0**; **no maintained tfjs / onnxruntime-web port exists**, and the *weights* licence is **unverified** (separate question from the code licence — this repo's NOTICE process already treats that distinction seriously) |
| **frame differencing / centroid** | <1ms | conflates all motion into one blob with 2+ subjects; fails on a still subject | trivial; useful only as a "did anything move" gate |

Facts worth recording so they are not re-derived: **`tracking.js` has no
optical flow at all** (its README lists it as a roadmap item that was
never implemented). **`cv.calcOpticalFlowPyrLK` IS in the stock
opencv.js** (it is in core `video`, whitelisted in
`platforms/js/opencv_js.config.py`), but stock opencv.js is ~8-9MB of
wasm; a custom build can reach ~2MB, which is still heavy next to a
1.04MB whole-app bundle. **No published browser/WASM benchmark of MOSSE
or KCF exists** — every FPS figure in circulation (600fps, 651fps) is
native C. Building either here means being the first public data point,
which is itself a reason to prefer something with precedent.

### 5.3 Recommendation

**Hand-rolled sparse pyramidal KLT on a 256x144 luma plane, studied from
`jsfeat` (MIT) and `speedy-vision` (Apache-2.0), running on the frame
the pipeline already has.**

Reasons, in order:

1. It is the only candidate that produces the **global-motion estimate
   §7 also needs**, from the same feature set, for free. Nothing else on
   the list gives two answers for one cost.
2. Two clean permissive references exist and one is actively maintained.
3. Failure is *observable*: surviving-feature count is a direct
   confidence signal, and "fewer than K features survived" is the
   hand-back-to-coast trigger. MOSSE's PSR is the analogous signal but
   requires an FFT to be correct first.
4. It carries no bundle weight — this is a few hundred lines, not a
   dependency.

**Fall back to NCC template match** if KLT's re-seeding proves fiddly:
the arithmetic above is within reach, it is auditable in one sitting,
and in a codebase that has been bitten repeatedly by instrument bugs
that is worth real money.

**Do not** reach for the learned trackers. A tracker that can lock onto
a visually similar distractor is a tracker that can move a cleared man's
patch onto the woman beside him, which is a new exposure path that does
not exist today.

### 5.4 The delivery question, and it is the actual risk

The frame has to reach R1 at 10Hz (not 30Hz — see below) without adding
a main-thread readback. Three options, ranked, all **unmeasured on
device**:

1. **Reuse the gate readback.** `gateTick` already does
   `drawImage(video, 0,0,16,16)` + `getImageData` at 10Hz on the main
   thread. Widen that canvas to 256x144 and hand the same buffer to both
   R1 and R2. One readback, one rate, no new plumbing. The unknown is
   whether a 256x144 `getImageData` stalls materially more than a 16x16
   one on an Adreno 610 — readback latency is usually dominated by the
   pipeline flush, not the pixel count, but "usually" is not a
   measurement.
2. **Worker-side, from the existing `createImageBitmap` transfer.** The
   worker already receives the full frame on every pass. But passes are
   gated at ~500ms+, so this gives R1 no more resolution in time than
   R3 has — it only helps if R1 is allowed to drive its own frame
   requests, which reintroduces a main-thread cost.
3. **WebGL, via speedy-vision's shader path.** Keeps the CPU free
   entirely, but adds a GPU dependency on the same queue that MoveNet
   and faceres are already contending for, on the device where GPU
   contention is the documented problem.

Start with (1). **10Hz, not 30Hz** — the render loop already
interpolates at rAF, so R1's job is to correct that interpolation, not
to replace it, and 10Hz is what the existing gate already pays for.

## 6. Association

### 6.1 What the standard trackers actually offer us

Licences verified from LICENSE files this pass. **abewley/sort is
GPL-3.0** and **nwojke/deep_sort is GPL-3.0** — that second one is
commonly assumed to be permissive and is not. **ifzhang/ByteTrack is
MIT** (but bundles Apache-2.0 YOLOX; check per-file if anything is ever
lifted). **noahcao/OC_SORT is MIT** (its LICENSE still carries
ByteTrack's copyright line — sloppy provenance, another reason to work
from the paper). **NirAharon/BoT-SORT is MIT** (the file is `/LICENSE`,
not `/LICENSE.txt`). **dyhBUPT/StrongSORT is GPL-3.0.** Every idea below
is taken from the paper, which is freely readable in every case.

**Take:**

* **OC-SORT ORU** (arXiv:2203.14360) — §3.4. The single best structural
  match: our normal operating state is what OC-SORT calls "the gap", and
  ours has the advantage of being *approximately known in length*.
* **BoT-SORT's state vector** (arXiv:2206.14651) — track `[x,y,w,h]`
  with independent `vw,vh` rather than SORT's `[x,y,s,r]` with `r`
  constant. We are already halfway there: `matchedStep` keeps `vw` and
  `vh` separately (`sizeVel(..., 'x')` / `'y'`). The remaining point is
  that no future round should reintroduce an aspect-ratio assumption —
  the criticism BoT-SORT makes of SORT is exactly that `r` held constant
  distorts the width estimate.
* **BoT-SORT's CMC** (camera-motion compensation) — this is the one the
  brief did not ask about and it may be the most valuable idea on the
  list for us, because it is the *same* estimate §7 needs. Their ablation
  on MOT17 (a benchmark dominated by static cameras) gives +0.64 MOTA /
  +1.62 IDF1 / +0.94 HOTA from CMC alone. Our footage is handheld vlogs
  with a measured motion p90 of 28.2 luma delta. Over a 1.5s gap, camera
  motion the tracker attributes to the *subject* compounds for the whole
  interval before anything corrects it. A translation-only estimate from
  the KLT features of §5.3 is enough; we do not need RANSAC-affine.
* **C-BIoU / buffered IoU** (arXiv:2211.14317) — the cheapest single
  upgrade over plain IoU on the whole list. Pad both the predicted track
  box and the observation by a fraction of their own size before
  computing IoU, run it twice (small buffer first, larger on the
  leftovers). It is a padding constant and a second loop. It directly
  addresses `birthNearMiss` — an observation that scored
  `0 < iou < PTRACK_IOU_MIN 0.2` against a live track and was re-minted
  as a new person, which the code's own comment already identifies as
  "churn, and it costs the subject their accumulated clear every time it
  happens". **That counter already exists and nobody has read it.**

**Do not take:**

* **ByteTrack's low-confidence second pass.** It solves a *within-frame*
  problem: the detector ran and emitted a weak box you were about to
  discard. We do not have weak detections between verdicts, we have
  *none*. Porting the two-threshold cascade would be solving a gap we do
  not have. (The generalised instinct — do not hard-drop a track the
  instant it is unmatched once — we already implement as `coastStep`.)
* **DeepSORT's appearance cascade.** GPL, and more importantly the
  matching cascade exists to stop stale tracks with diffuse covariance
  from stealing detections in a crowded scene. With 1-4 subjects that
  ambiguity is rare, and we already have the *cheap* half of appearance
  gating: `IDENT_SIM_MIN 0.15` in `matchedStep` and
  `identity-memory.mjs`. Both use the faceres descriptor we compute
  anyway, so there is no embedding network to add — and the descriptor's
  separability is documented as poor (17% of different-person pairs
  score >= 0.9 against a same-person p05 of 0.28), which is exactly why
  it is used as a *gross-mismatch veto* and not as a matching cost. That
  is the right call and should stay.
* **StrongSORT's AFLink / GSI** — offline post-processing. Not
  applicable.
* **StrongSORT's NSA-Kalman** — scaling process noise by
  `1 - confidence` is free and correct in principle, but we do not run a
  Kalman filter and I am not proposing one (see below).

### 6.2 Should we introduce a Kalman filter?

**No, and this is a deliberate refusal.** The argument for one is
principled uncertainty propagation; the argument against is that
C-BIoU's own result is that under irregular motion a Kalman filter's
smoothness assumption is *part of the problem*, and our subjects sit
down, turn, and are re-framed by a handheld camera. We would be adding a
covariance we cannot validate, on a device where every previous "more
principled" mechanism that could not be measured end-to-end (the R13
identity bank, the 1070 person skip) shipped a regression. The EMA plus
an explicit `missMs` is a filter whose behaviour is legible in the
counters we already have. Revisit only if E5 (§10) shows association
errors a covariance gate would have caught.

### 6.3 The concrete association proposal

Ordered, smallest first:

1. **Read `birthNearMiss` and `birthContended` on the corpus and on his
   phone.** They ship today and nobody has quoted them. If near-miss
   births are a large share, (2) is worth building; if they are not, it
   is not.
2. **Buffered IoU, two-stage.** Pad by `BIOU_PAD_1` (start 0.1 of own
   size) for the first pass, `BIOU_PAD_2` (0.3) for the leftovers,
   against the same `PTRACK_IOU_MIN`. Keep `sizeCompatible` unchanged —
   it exists because an oversized stale track becomes immortal, and
   buffering makes that risk *worse*, not better.
3. **Associate the verdict against the track's box at observation time**
   (§3.4 step 2). Requires the R1 ring.
4. **Global-motion compensation of the predicted box** before IoU
   (§7.2), using the estimate R1 already produces.

Greedy-by-descending-IoU is kept. With <= 6 tracks the difference from
Hungarian is negligible and greedy is auditable.

## 7. Scene cuts

### 7.1 What is already right, and what is not

Right: `gateTick` **demotes rather than wipes** (`demoteTracks`), keeps
the boxes so coverage holds through the pass gap, and banks
`clearStreak: 1` for a track that was cleared — so a demoted man needs
one read, not two, to get his clear back. That is already the "graceful
response" the brief asks for, and it should be credited rather than
rebuilt.

Not right, in descending cost:

1. **The detector is a fixed threshold on a metric whose baseline
   moves.** `CUT_DELTA` was 28 sitting exactly on the p90 (28.2) of his
   footage's ordinary handheld motion. It is 50 now, in the gap between
   motion p90 28.2 and cut p95 54.9. That is a better constant on one
   distribution from one phone on one video. It is still a constant.
2. **A cut also does `passEpoch++`, which drops the in-flight pass.**
   Measured: `passDropped` 29 against 39 cuts in one 90s window. So a
   false cut costs a demotion *and* the verdict that would have undone
   it. That is the coupling that makes false cuts expensive.
3. **`wipeIfEmpty` still wipes on `sceneCut && big`** — one pass, no
   streak, if the previous max subject height was >= `WIPE_SMALL_H
   0.25`. Both of that eraser's measured misfires were it erasing people
   who were still there.

### 7.2 Better detection, at near-zero cost

The literature answer is unambiguous and it is not a new metric. The
TRECVid seven-year retrospective (Smeaton, Over & Kraaij, CVIU 2010)
found colour histograms plus a flash-rejection step dominated, and
recorded bluntly that "despite continued introduction of novel
approaches each year... these novel approaches do not lead to
improvements in effectiveness". Lienhart's comparison found plain
colour-histogram difference reached ~95% recall at ~5% false hits, and
that **"hard cut detection based on the edge change ratio does not
outperform that based on the colour histogram differences, although the
computational burden is much greater"** — so ECR is refuted on both axes
and should not be built. Ranked shortlist for our ~1ms budget:

**(a) ffmpeg's `scdet` transform — the top recommendation, and it is
three lines.** From `libavfilter/vf_scdet.c`:

```
mafd  = SAD(luma_t, luma_{t-1}) normalised to 0..100   // == our meanAbsDelta
diff  = |mafd - prev_mafd|
score = clamp(min(mafd, diff), 0, 100)
```

Read what that does to our exact failure. During a pan, `mafd` sits on
an elevated but *slowly varying* plateau, so `diff` is small, and
`min(mafd, diff)` collapses to the small term. At a genuine cut, `mafd`
jumps *and* `diff` is large, so the min stays large. It is a discrete
first derivative of the metric we already compute — one subtract, one
min, one extra float of state, no window, no division, no motion
estimate. It is shipped production code in a tool everyone uses, and it
targets precisely "elevated-but-smooth baseline from camera motion".

**(b) PySceneDetect's `AdaptiveDetector` ratio, as a second line.**
(BSD-3-Clause.) Ratio of the current delta to the mean of the last ~4
deltas, fire on `ratio >= 3.0` **AND** `delta >= min_content_val 15.0`.
The second clause is load-bearing: without it a quiet scene's near-zero
baseline makes any flicker an enormous ratio. Use a *causal* window
(PySceneDetect's is centred) and a **median**, not a mean, so a real cut
inside the window does not contaminate the baseline it is being compared
against. Complementary to (a): (a) handles smooth drift, (b) handles a
baseline that is elevated *and* jittery.

**(c) If (a)+(b) do not close it: projection-profile global motion.**
Sum the luma plane along rows and along columns, 1D-correlate each
against the previous frame's profiles over a small shift range, subtract
the estimated global translation, then re-score. At 16-32 samples per
axis brute force is trivial and no FFT is needed. This is also the same
answer §6.1's CMC wants, and if §5 ships KLT the estimate is already
there for free — at which point (c) costs nothing and should simply be
adopted.

**Do not build:** edge change ratio (refuted above, and the original
paper's own figure is ~15fps on a 1999 workstation for that signal
alone); histogram-distance refinements (chi-square / Bhattacharyya /
EMD) over the existing MAD — no verified evidence they are needed for
cut detection and EMD is disproportionately expensive; TransNetV2
(MIT, F1 77.9 ClipShots / 96.2 BBC / 93.9 RAI — quote it as the accuracy
ceiling, it is a conv net per 100-frame window and is not a candidate).

### 7.3 A graceful response

Three changes, each independently shippable:

1. **Grade the response by confidence.** Two thresholds instead of one:
   `CUT_STRONG` -> demote as today; `CUT_WEAK` -> **do not demote**, but
   (i) force an immediate verdict pass, (ii) suppress `wipeIfEmpty`'s
   `big` shortcut for one interval, (iii) clear `heldPersons`. The
   forced pass is the part that is actually valuable at a cut ("cuts are
   where new people appear"); the demotion is the part that costs a
   cleared man his clear. **They do not have to be bought together, and
   today they are.**
2. **Do not drop the in-flight pass on a weak cut.** `passEpoch++` on
   `CUT_WEAK` throws away the very evidence that would resolve the
   ambiguity. On a strong cut it stays — those observations really do
   describe a frame that no longer exists.
3. **Re-associate across a strong cut by appearance, not position.**
   `demoteTracks` currently drops `desc` deliberately ("whoever stands
   there in the new shot is unknown"). That is correct for *association*
   and it also throws away the only thing that could give the man his
   clear back in one read instead of two. The identity memory is the
   right home for this and it already is the mechanism — but only once
   §2 lets it act on a birth. **§2 is a prerequisite for making cuts
   cheap**, which is a second, independent reason to build it first.

## 8. The verdict state machine

### 8.1 The hypothesis the brief proposes, tested and refuted

The brief says: "clearing a subject requires 2 consecutive certain reads
plus a 1.5s hold; at 1.5s per verdict that is a 3-second floor of blur
on every newly-born track, which is a large share of our false cover."

Measured today, man mode, his regime:

| arm | EXPOSURE | FALSE COVER | PHANTOM |
|---|---|---|---|
| shipped (`GENDER_INSTANT_CLEAR` 0.80, `CLEAR_STREAK_N` 2) | 81.0s | 216.5s | 144.0s |
| instant 0.70 | 82.0s | 215.0s | 144.0s |
| instant 0.60 | 82.0s | 213.5s | 144.0s |
| instant 0.50 | 82.5s | 210.5s | 143.5s |
| instant 0.45 (= the clear bar; every certain read is instant) | 82.5s | 210.0s | 142.5s |
| `CLEAR_STREAK_N` 1 | 82.5s | 210.0s | 142.5s |
| `CLEAR_STREAK_N` 1 + instant 0.60 | 82.5s | 210.0s | 142.5s |

**The entire ladder is worth 6.5 seconds of 216.5.** Collapsing it
completely — making every certain read an instant clear — recovers 3%
and costs 1.5s of exposure. This matches, and explains, the earlier
finding recorded in `identity-memory.mjs` that `CLEAR_STREAK_N` 2 -> 1
recovered 11s of 241s.

The reason is §0: the ladder is evaluated in `matchedStep`, and the
covering id survives a median of one frame. You cannot climb a ladder
you are thrown off before the second rung. **B1 is the same idea as
"lower the streak", applied at the one place where it is reachable, and
it is worth 106.5s instead of 6.5s.**

This is the most important negative result in this document, because
"lower the streak" is the obvious proposal and it is nearly worthless.

### 8.2 The replacement, and how much of it to build

Given §8.1, a full log-odds rebuild is **not** justified by anything
measured. It should be designed now and built only if E6 (§10) shows the
residual is evidence-combination rather than churn. The design, for when
it is:

**Accumulator.** Per track, a log-odds evidence score for "this subject
must be covered", in the standard binary Bayes filter form (Elfes /
Moravec; Thrun, Burgard & Fox, *Probabilistic Robotics*):

```
l_t = clamp( gamma * l_{t-1} + ( log(p_t/(1-p_t)) - l_0 ),  L_MIN, L_MAX )
```

* `p_t` — the calibrated probability that this read means "cover".
* `l_0` — prior log-odds. Seeded from the identity memory when a
  descriptor matches a trusted identity, and from the neutral prior
  otherwise. **This is where a per-subject prior belongs, and it is the
  only place a prior should enter.**
* `gamma < 1` — exponential decay toward the prior, so evidence ages.
  This is what replaces `CLEARED_TTL_MS` and `CLEAR_DECAY`, both of
  which are ad-hoc versions of the same idea. Time constant
  `tau = -1/ln(gamma)` in verdicts; start `tau` ~ 3 verdicts so a clear
  survives one bad read and not three.
* `clamp` — **load-bearing, and the reason to write it down.** This is
  the OctoMap fix (Hornung et al., *Autonomous Robots* 2013): without
  clamping, a long consistent run drives `l` toward infinity and the
  filter freezes — a subject who has read clear thirty times becomes
  effectively unrevocable. Clamping guarantees a bounded number of
  contrary reads can always flip the decision. This is exactly the
  failure mode `CLEARED_TTL_MS` was bolted on to prevent, expressed
  properly.

**Decision.** Two thresholds with a dead zone (Schmitt), *not* one:
cover when `l >= L_COVER`, uncover when `l <= L_CLEAR`, hold otherwise.
The asymmetry goes **in the thresholds, never in the prior** — the
Bayes-optimal threshold under asymmetric cost is
`tau* = C_fp / (C_fp + C_fn)`, and with `C_fn >> C_fp` that pushes
`tau*` toward 0, i.e. cover on weak evidence. Keeping the accumulator an
unbiased posterior and putting the cost only at the decision point is
what keeps intermediate readings interpretable in a diagnostics ring —
which in this repo is not a nicety, it is how every bug this month was
found.

**Safety, stated as an invariant a test can check:** `l` is initialised
at or above `L_COVER` for every new track unless the birth read is
`!flagged && instant` (§2). An absent read contributes exactly zero. A
read that carries no descriptor signal contributes exactly zero. There
is no path from "no evidence" to "uncovered".

**Uninformative reads.** In a log-odds framework a read that carries no
information has `p ~ p_0` and therefore contributes `~ 0` automatically
— that is the elegant part. The catch is that you cannot detect such a
read *from the score*: `p ~ 0.5` is equally consistent with "the model
knows nothing" (epistemic — should be a no-op) and "the model knows a
lot and the answer is genuinely 50/50" (aleatoric — should count,
weakly). **You need a signal independent of the score, and this repo
already has one and has already measured it**: `nm`, the faceres
descriptor magnitude before L2 normalisation — p50 **12.66** on reads
that carry signal against **2.88** on the model's prior, with pearson
0.464 against `|v-0.5|` overall but collapsing to -0.21..+0.30 inside a
narrow `v` slice, i.e. **not the sigmoid restated**. The shipped
`inertNoSignal` treatment (a no-signal read becomes `positionOnly`
rather than an abstention) is already exactly the right treatment. It
should become the *definition* of a zero-weight read in the accumulator.
Chow's reject-option rule (Chow 1970, IEEE TIT 16(1):41-46) is the
classical framing, and its limitation is precisely this: it rejects on
the posterior itself, which cannot separate the two cases.

**Calibration is a prerequisite, not an improvement.** `log(p/(1-p))` is
only a valid log-likelihood ratio if `p` is calibrated; an overconfident
model produces increments that are systematically too large and the
filter crosses its boundaries faster than the nominal error rates
assume. Temperature scaling (Guo et al., ICML 2017, arXiv:1706.04599) is
the one-parameter fix. **And it is monotone, so it cannot change the
ROC** — this repo already proved that by measurement
(`clear-bar-roc.mjs`: "temperature scaling and moving
`GENDER_CLEAR_SCORE` are THE SAME MOVE"). Nobody should re-derive that.

**SPRT is the wrong frame here** and it is worth saying why. Wald's SPRT
is optimal (Wald-Wolfowitz) under the assumption that the observations
are i.i.d. from one fixed hypothesis. Our stream's hypothesis changes
constantly — a cut, a re-association, a different person walking into
the track. A cumulative LLR with no forgetting takes an unbounded time
to unlearn strong pre-change evidence. The standard fixes (truncated
SPRT, sliding-window SPRT) converge on exactly the clamped, decaying
accumulator above; and CUSUM, which *is* a repeated SPRT that restarts
at zero (Lorden 1971), is the right tool for the *cut* question in §7,
not for the *cover* question here. Adams & MacKay's BOCPD
(arXiv:0710.3742) is the principled version of §7 and is too expensive
per subject.

### 8.3 What to keep from today's machine regardless

* **Flag is instant.** Never negotiate this.
* **The abstention grace** (`graceSpend`) and its three unconditional
  spends (`childAbstain`, `faceFound === false`, `lastVerdict !==
  'clear-certain'`). Each was measured into place; the log-odds form of
  the same thing is a zero-weight read for the readable abstention and a
  positive-weight read for the no-face case.
* **`IDENT_SIM_MIN 0.15` as a gross-mismatch veto.** Not a matching
  cost. §6.1.

## 9. Prediction and pre-emption

Can we cover before the verdict arrives? **We already do, and it is the
architecture's foundation: a new track is born blurred.** The question
is really whether we can be *more* pre-emptive without opening exposure,
and there are exactly two safe moves and one unsafe one.

**Safe — pre-emptive cover on a motion-predicted box.** Extrapolate a
blurred track's box forward by its velocity and *grow* it. The existing
render path already does the right thing here and the reasoning is
recorded in `matchedStep`: **grow at full alpha, shrink slowly.** Every
error in that scheme over-covers. The extension worth making is that R1
(§5) replaces the extrapolation with a measurement, so the patch is
correct rather than merely large.

**Safe — pre-emptive cover across a cut.** On a strong cut the tracks
are demoted to blurred and the boxes are kept. The frames between the
cut and the forced verdict are covered by the *previous* shot's
geometry, which is wrong but in the covering direction. This is already
what happens; the note in `gateTick` explains why a full-frame blackout
was measured and refused (cuts every ~2.8s meant the player spent most
of its life fully blurred).

**Unsafe, and it must be named so it is not proposed — pre-emptive
*uncover*.** Predicting that a subject who has been clear will still be
clear, and lifting the patch before the verdict confirms it. That is the
only direction in which prediction can create exposure, and it is
exactly what §2's B2 arm edges toward. B1 is not this: B1 does not
predict anything, it applies a verdict that has *already arrived* to the
track it arrived about.

**The safe direction of every error in the proposed scheme, enumerated:**

| mechanism | if it is wrong, what happens |
|---|---|
| R1 flow tracker loses lock | fewer features survive -> hand back to `coastStep` -> track expires -> next verdict re-mints it **blurred**. Covering. |
| R1 flow tracker drifts | patch is in the wrong place -> **phantom** at the drift site and possible **exposure** at the true site. **This is the one genuinely two-directional risk in the design** — see §12. |
| Global motion estimate is wrong | predicted box is misplaced -> association fails -> new track -> born **blurred**. Covering. |
| Buffered IoU matches the wrong track | a cleared track absorbs a woman's observation -> **exposure**. Bounded by `IDENT_SIM_MIN`, `sizeCompatible`, and the fact that a flag is instant on the next verdict. Two-directional; must be measured (E5). |
| ORU re-fits the box wrongly | box misplaced by at most the inter-verdict displacement. Same as drift. |
| `CUT_WEAK` misses a real cut | tracks are not demoted -> a stale cleared track may absorb the new shot's subject -> **exposure**. This is why `CUT_STRONG` keeps the current behaviour and `CUT_WEAK` only *adds* a forced pass. |
| Birth clear (B1) fires wrongly | one verdict interval of **exposure**. Priced: +2.5s man / +4.5s woman. |
| MoveNet marked `'absent'` | every derived predicate undefined -> defaults chosen to cover. Covering **by construction**, which is the whole point of the three-state. |

## 10. How each proposal is measured

The repo's standard: name the arm, what it holds constant, and what
result kills the idea. All of these run against
`Z:/tamescroll-corpus/bank` (18 windows, 3,465 reads, 107 labelled
clusters, 93.7% coverage) unless they say device.

**E1 — B1's exposure cost, attributed.** `bench/matrix.mjs`-style arm,
per-window rather than aggregate, B0 vs B1, both modes. Constant: every
other opt (`hold`, `clampPad`, `cut`, `inertNoSignal`, `memSignal`,
`mem`). **Kills it:** the +2.5s concentrated in one or two windows on
one subject, i.e. a single confidently-misread woman rather than a
diffuse cost. Then render those frames and look.

**E2 — B1 on the render, not the score.** `bench/export-frames.mjs` over
the windows whose numbers moved, B0 against B1, judged by eye against
the five failure classes. **Kills it:** a patch visibly flickering off
and back on within a second — the score cannot see that and the owner
can.

**E3 — the cost of a verdict pass without MoveNet, on his phone.**
Device A/B on a built APK, reading the existing `stage` marks
(`persons`, `fullFaces`, `crops`, `end`) plus `lastVerdictMs`, over a
90s watch page, both arms in the same regime (assert `slotsNonZero 0` in
both, or the pair is not clean — this repo has lost two rounds to
comparing different MoveNet regimes). **Kills it:** the crop stage, not
MoveNet, dominating — in which case the clock lever is
`ZOOM_MAX_PERSONS` and §4 is re-priced.

**E4 — does the phantom guard scale with the clock?** `cadence-ab.mjs`
crossed with the null-mint hold on/off and `NULL_MINT_NM_FLOOR` swept.
**Kills the clock as shippable:** phantom rising faster than linearly in
verdict rate with the guards on. 144 -> 260.5s at 3x is already
sub-linear; the question is whether it stays there.

**E5 — association errors, counted rather than inferred.** Read
`birthFresh` / `birthNearMiss` / `birthContended` / `birthSizeRejected`
/ `sizeRejected` / `coastExpired` on the corpus **and** on his phone.
These all ship today and none has been quoted in a session summary.
**Kills buffered IoU:** near-miss births being a small share of all
births — then the churn is coast expiry, not threshold refusal, and
§5 (survival) is the fix rather than §6 (matching).

**E6 — is the residual false cover evidence-combination or churn?**
After B1, re-run `fc-why.mjs`. Today it reads: misread false cover
149.0s of 216.5s, of which `other` 115.0s (77%), `weak` 21.0s (14%),
`nosignal` 11.5s (8%), `misgender` 1.0s (1%). **If `other` collapses
after B1, §8.2's log-odds rebuild is not justified and should not be
built.** That is the gate on the most expensive proposal in this
document.

**E7 — the cut gate, both halves.** (a) Re-run
`bench/corpus-cuts.mjs` with the `min(mafd, |dmafd|)` transform and
compare fire rate against `bank/cuts.json` and against a hand-labelled
cut list for two windows. (b) `arch-arms` cut arm with demote decoupled
from forced-pass. **Kills the transform:** a real cut whose `mafd` was
already elevated (a cut *from* a high-motion shot *to* another
high-motion shot) scoring low — the `min` suppresses exactly that case
and it is the transform's known weakness.

**E8 — the flow tracker, offline before it is on a device.**
`Z:/tamescroll-corpus/video/*.mp4` are present and `corpus-lib.grabRaw`
decodes at the app's own 640x360, so a KLT arm can be scored offline
against real pixels at 10Hz between the 2fps banked verdicts. Arm:
`matrix.mjs` `position` mode where the position observation comes from
**flow**, not from a synthetic full-width body. **Kills it:** drift
producing exposure at the true site, or the arm scoring no better than
`coast` — in which case the tracker buys patch smoothness only, which is
a cosmetic win and should be priced as one.

### 10.1 The trap, stated precisely

The brief names it as "the offline corpus is a native-resolution
instrument and the device is not". That is half of it and the smaller
half. The corpus is banked at **640x360 — his measured decode** — so
resolution is *not* the main gap for this corpus. The gap is
**execution fidelity**: corpus men read `v` p50 **0.864** where his
phone read **0.657** on the same video, and **2.3%** of corpus
clear-bar reads carry no descriptor signal against **36-42%** on his
phone, because faceres' descriptor magnitude alternates 11.0, 1.1, 3.8,
11.0, 0.2 on the *same subject* on his GPU — 57 flips in 116 reads.

The consequence for everything above: **an arm whose benefit depends on
reads being informative will read better offline than it performs.** B1
is partly exposed to this (a birth clear needs `instant`, i.e. a strong
read, and his phone produces those less often), so **its corpus benefit
is an upper bound**. Conversely `inertNoSignal` and the `nm` floor are
*more* valuable on his phone than on the corpus, and any sweep of them
that reads flat offline is a broken instrument, not a null result — as
three sweeps in loop 40 were.

The device-side check that closes this for B1 is cheap: read
`clearGracePaid`, `birthFresh` and a new birth-clear counter over 90s on
his phone, against `readClearCertain`. A birth clear nobody has seen
fire is a claim.

## 12. What I am unsure about, bluntly

1. **The +2.5s exposure on B1 is not attributed.** It is small and it
   appears in both modes, which is reassuring, but 2.5 seconds could be
   one woman sharp for five frames in five windows or one woman sharp
   for twenty-five frames in one. Those want different responses. E1
   before shipping.

2. **The biggest risk in my own design is the flow tracker (#7), and it
   is the only two-directional error in the whole proposal.** Everything
   else fails toward covering by construction. A drifting KLT track
   moves a *solid* patch off the person it is covering and onto
   background — exposure at the true site and phantom at the drift site,
   simultaneously, with every counter healthy. And it is the failure the
   score is worst at seeing, because `corpus-score.mjs` only knows about
   faces the detector found. If #7 is built it needs a hard leash that
   is not a threshold: an absolute cap on how far a box may move without
   a verdict confirming it (say one box-width), and a surviving-feature
   floor below which R1 refuses to speak at all and the track falls back
   to `coastStep`. I would rather ship a tracker that gives up often
   than one that is confidently wrong.

3. **The phantom cost of the clock may be understated.** 144 -> 260.5s
   is corpus phantom, and the corpus decodes clean frames. On his phone
   36-42% of reads carry no descriptor signal, and a no-signal read is
   exactly the population the null-mint hold is guarding against. Three
   times the births could be worse than three times the phantom there.
   E4 is a corpus experiment and cannot fully answer it; the honest
   answer needs his rings.

4. **I have not verified that `obs.instant` is reachable often enough on
   his hardware for #1 to pay there.** The corpus says instant-eligible
   male reads are ~34% of same-gender reads; his phone reads lower
   overall (`v` p50 0.657 vs 0.864). If the instant bar is rarely
   reached on his device, #1's device benefit is a fraction of its
   corpus benefit — and the response is *not* to lower
   `GENDER_INSTANT_CLEAR` (§8.1 shows that is worth ~2s), it is to let
   the **identity memory** be the birth-clear authority, which §2
   already enables and which fires 359 times in man mode with zero
   reachable wrong firings.

5. **Everything about §8.2 is design, not measurement.** I believe the
   log-odds form is the right final shape and I do not believe it is
   justified yet. If E6 shows `other` collapsing after B1, it should not
   be built at all this quarter.

6. **Unverified in the literature survey**, flagged by the researchers
   themselves and repeated here rather than laundered: no published
   browser/WASM benchmark of MOSSE or KCF exists; `speedy-vision`
   publishes no mobile performance numbers; NanoTrack's *weights*
   licence is unconfirmed (the code is Apache-2.0); the projection-
   profile motion estimate is sound engineering but no shot-detection
   citation could be pinned to it; and the twin-comparison and
   histogram-metric claims in the cut survey are general CV knowledge
   rather than re-verified primary sources.

## Appendix — reproducing the tables

`bench/cadence-ab.mjs`, `bench/fc-why.mjs` and `bench/churn.mjs` are in
the tree and were run as-is. The birth and instant sweeps were run from
the scratchpad as throwaway scripts (no repo file was added) that patch
`bench/.cache/shipped.mjs` and load the variant, in the same style as
`bench/matrix.mjs`. The patch anchors, so they can be rebuilt:

* instant / streak: `var GENDER_INSTANT_CLEAR = 0.8;` and
  `var CLEAR_STREAK_N = 2;`
* birth: the literal block in `newTrack`,
  `    state: "blurred",` followed by `clearMs: 0,` `missMs: 0,`
  `clearAge: 0,` `clearStreak:` — with `"blurred"` replaced by the guard
  expression.

Both scripts `throw` if the anchor is absent, because a constant sweep
that cannot move is a broken instrument and not a null result — this
repo has lost three sweeps to exactly that.

Arm options held constant in every table above:
`{ hold: true, clampPad: 0.02, cut: true, inertNoSignal: true,
memSignal: true, mem: 'loose2' (man) / 'loose' (woman) }`, thinned with
`mode: 'coast'`, which is his measured regime.
